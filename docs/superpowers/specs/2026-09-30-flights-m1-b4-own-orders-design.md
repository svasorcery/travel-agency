# Flights M1 B4: список своих заказов — проект спецификации

**Статус:** реализация разрешена 2026-10-01 после уточнения подгрузки и возврата. Вариант A используется как ограничение существующего backend-контракта.

**Уточнение UX:** автоматически подгружаем следующую порцию при приближении к концу ленты, оставляем кнопку «Показать ещё» и сохраняем точное место возврата из B3 в памяти той же вкладки. Автоподгрузка не перемещает фокус; явная кнопка переводит его к первому добавленному заказу.

**База:** `git fetch origin dev` 2026-09-30; `origin/dev` = `53df375368c1d4fe5b53fe1d3514d2754059e7ed` (merge PR #21). `FETCH_HEAD` и текущий `HEAD` совпали с этим SHA; обе проверки ancestry между `HEAD` и `origin/dev` прошли. Перед будущей реализацией заново проверить базу и ancestry, не заменять запрошенную базу текущим `HEAD`.

## Цель и граница

Авторизованный пользователь открывает `/flights/orders`, видит страницы только своих уже спроецированных заказов и переходит по `aggregateId` на существующую страницу B3 `/flights/orders/:aggregateId`. Прямой вход в список и возврат после входа работают после перезагрузки. Список не создаёт, не подтверждает и не отменяет заказы. Кнопка отмены не входит в B4.

Токены живут только в памяти. В URL допустим только непрозрачный `aggregateId` существующего B3 маршрута; данные пассажира, email, телефон, provider ref и токены туда, в browser storage и логи не помещаются. Демо использует вымышленные данные и локальный stub, без реальных поставщиков, платежей и Anthropic. Миграции и деплой не входят в работу.

## Проверенный контракт на базе PR #21 до B4

- `ListOrdersEndpoint.Get` — авторизованный `GET /api/flights/orders`, параметры `limit=50`, `offset=0`. `TryGetUserId` извлекает непустой GUID из claims; клиентский user ID сервер не принимает. Запрос `ListOrdersQuery(userId, limit, offset)` идёт в EF read model через `ListOrdersHandler` и `OrderReadModelQueries`.
- EF фильтрует `UserId == userId`, сортирует по `BookedAt DESC`, применяет `Skip/Take`. `limit` ограничен диапазоном 1–200, отрицательный `offset` заменяется на 0. Ответ `OrderListResponse` содержит `items: OrderResponse[]`, `limit`, `offset`, без `total`, `hasMore`, cursor или версии проекции.
- Элемент имеет `aggregateId`, `status`, сумму/валюту, itinerary, ticketNumbers и четыре времени. `BookedAt` — время hold. Имя, контакт и другие данные пассажира не входят в `OrderResponse`. Quote до hold в EF-списке отсутствует; создание и обновление read model eventual.
- B3 уже имеет типизированный runtime-проверяемый single-order GET, клиентский маршрут, owner-bound краткий сигнал успешного hold/confirm и ограниченный polling. На direct URL после потери токена страница предлагает вход. `FlightsAuthService.beginLogin` сейчас разрешает return path конкретного заказа, но не `/flights/orders` как путь списка; без правки логин со списка вернёт на `/flights`.
- Демо-stub сейчас реализует GET одного заказа, но не GET списка. Его `Map` живёт только пока работает stub, fake auth не проверяет JWT и владельца. Текущие тесты покрывают owner-фильтр и базовые limit/offset в `OrderQueriesTests`, 401/некорректный identity/200 в HTTP fixture и B3 direct URL. Тестов HTTP query binding, формы list DTO, tie-breaker и demo list пока нет.
- Для list/get backend применяет `[Authorize]`, без policy `flights:book`; web-клиент B2/B3 валидирует наличие этого scope, `aud=travel-web` и GUID `sub`. Для B4 сохранить текущий web auth gate. Если нужен отдельный читатель без права бронировать, это новый auth-контракт и отдельное решение. Live issuer/callback для нового list path здесь не проверен.

Источники: `modules/flights/Travel.Modules.Flights.Api/Endpoints/ListOrdersEndpoint.cs`, `Contracts/Contracts.cs`, `Application/Queries/OrderQueries.cs`, `Infrastructure/Persistence/{OrderReadModelQueries,OrderReadModelEventApplier}.cs`, `tests/flights/Travel.Modules.Flights.Tests.Integration/Booking/OrderQueriesTests.cs`, `tests/Travel.Host.Tests.Integration/Flights/FlightsEndpointsHttpTests.cs`, `shared/ts/api-client/src/flights-booking.*`, `apps/web/src/app/flights/{flight-order-page.component,flights-auth.service}.ts`, `tools/demo/flights-search-api.mjs`.

## Варианты контракта и решение для согласования

| Вариант | Поведение и цена |
| --- | --- |
| **A. Существующий offset + lookahead (выбран для B4)** | Добавить вторичную сортировку `AggregateId DESC` при равном `BookedAt`. Клиент запрашивает `limit=21`, добавляет до 20 карточек в ленту; 21-й служит признаком следующей порции, `offset` увеличивается на 20. Не нужны новые поля DTO, миграции или подсчёт всех строк. При вставке/перепроекции между запросами offset может сдвинуться и дать повтор/пропуск. Повтор ID не создаёт вторую карточку, но это не восстанавливает пропущенную запись. Не обещать полный снимок или общее число заказов. |
| B. Keyset cursor по `(BookedAt, AggregateId)` | Устойчивее при вставках перед текущей страницей, но требует нового API-контракта, фильтра, cursor DTO и тестов. Изменение статуса существующей строки остаётся eventual. Выбирать, если гарантированная непрерывная пагинация — требование B4. |
| C. Первые 50 без навигации | Дешевле, но скрывает более старые заказы и не исполняет задачу списка для пользователя с >50 заказами. Не рекомендуется. |

Для A отсутствие `total` решается lookahead, а не выдуманным числом. Равные `BookedAt` требуют вторичной сортировки; это узкая backend-правка без изменения схемы. Даже с ней offset не даёт консистентного снимка при изменениях. На странице не показывать «всего N». Если продукту нужен полный стабильный проход по истории при конкурентных вставках, согласовать B перед реализацией.

Ещё один контрактный пробел: list отдаёт полный `OrderResponse` для каждого элемента, включая ticketNumbers, хотя карточке нужны статус, сумма, маршрут и время. B4 использует существующий DTO, не отображает билетные номера и не хранит ответы вне памяти; отдельный summary DTO потребует backend API-расширения и оправдан при большем масштабе/требовании минимизации payload. `OrderResponseMapper` при повреждённом itinerary может отдать пустой маршрут; runtime decoder B3 отклоняет такой элемент. Для B4 предлагается отклонять всю повреждённую страницу с явной ошибкой и ручным повтором, не показывать неполный маршрут как корректный заказ.

На list-ответе сейчас нет явного `Cache-Control: no-store`. Добавить его на B4 endpoint и покрыть HTTP-тестом, чтобы браузер/промежуточный кэш не сохранял историю поездок. `HeldUntil` в `OrderResponse` отсутствует: список не показывает обратный отсчёт или срок hold; детальная страница B3 уже объясняет это ограничение.

## Экран и состояния

- На `/flights` есть «Мои заказы», на B3 — «К списку заказов». Все переходы внутри этого пути используют Angular RouterLink, чтобы не терять память приложения. `/flights/orders` — Client render, не использует route query для глубины ленты и при полной перезагрузке начинает с первой порции после входа. Ссылка на карточке ведёт только на B3 `/flights/orders/{aggregateId}`. В списке показываются направление(я), статус Held/Confirmed/Ticketed/Cancelled/Refunded, сумма с валютой и «Удержание создано» из `bookedAt`; нет пассажира, provider ref, ticketNumbers и действия отмены.
- Anonymous/потерянная сессия: приглашение войти, ни одной старой карточки. OIDC callback возвращает именно на `/flights/orders`; после проверки `aud=travel-web`, непустого GUID `sub` и `flights:book` загружается страница 1. При ошибке входа — сообщение и повтор входа. При 401 очистить видимые данные и предложить вход; при 403 — не показывать данные и объяснить недоступность.
- Первая загрузка: явный `aria-busy`/status. Успешный `items=[]` на offset 0 — «Пока нет отображаемых заказов», пояснение про задержку, ручное «Обновить список» и путь к поиску. Загрузка следующей порции сохраняет все предыдущие карточки и их порядок. Пустая следующая порция означает конец доступной ленты, не глобальную пустоту.
- При известном в этой вкладке успешном hold B3 передаёт списку owner-bound hint без PII. Пока новый заказ отсутствует в первой странице, список показывает отдельное «Данные обновляются» и делает ограниченный GET первой страницы каждые 2 секунды до 30 секунд. Он не рисует синтетический заказ и не называет пустую проекцию окончательной. По истечении окна polling останавливается, остаётся ручной refresh. После confirm статус видимой строки тоже может запаздывать; его проверяют ручным refresh или на B3-странице, без обещания мгновенного обновления списка. Для прямого URL/перезагрузки без hint автоматический polling не включается: список не может доказать существование невидимого заказа.
- «Обновить список» явно сбрасывает ленту на первую порцию и верх страницы. При ошибке первой загрузки нет ложной пустоты. При network/timeout/malformed следующей порции предыдущие проверенные карточки остаются, автоматические попытки останавливаются, «Повторить загрузку» повторяет тот же offset. При 401/403 все карточки и snapshot удаляются. Поздние ответы после нового поколения запросов, ухода или смены owner отбрасываются.
- UI не добавляет client-side owner фильтр как замену серверу; проверка владельца остаётся в JWT + EF. Краткий hint и результаты в памяти привязаны к user ID. Номер страницы, токен, DTO и PII в storage не записываются. Состояние списка не отражает авторитетность записи в Marten и может запаздывать.

## Уточнение фронтенда: автоподгрузка, фокус и возврат

1. Обычный семантический `ol` со ссылками на заказы. IntersectionObserver на конце ленты с упреждением 400px вызывает общий loader; одна порция 20, одновременно не более одного GET. Кнопка «Показать ещё» остаётся доступной, в том числе при отсутствии IntersectionObserver. Само получение фокуса кнопкой не запускает запрос и не перехватывает Tab.
2. Автоматическое добавление не перемещает фокус. Явная активация кнопки после успеха переводит фокус на первую новую ссылку. Если автоматический ответ приходит, пока пользователь уже сфокусировал кнопку, его проверенные данные ждут в памяти до её активации, без второго GET и без перестановки элементов вокруг фокуса. Ошибка не создаёт бесконечных повторов; одинаковые ID сливаются без новой карточки, offset продвигается по server batch, не по числу уникальных карточек.
3. Перед переходом в B3 сохраняются загруженные порции, следующий offset, hasMore, выбранный aggregateId, его верхняя координата относительно viewport, общий scrollY и ссылка с фокусом. Snapshot единственный, привязан к текущему owner и живёт только в памяти вкладки. Он не содержит токенов и не записывается в history.state/storage/URL. Logout/смена owner удаляет его немедленно.
4. Браузерный Back и «К списку заказов» из B3 сначала проверяют текущий token/session, затем синхронно восстанавливают карточки из snapshot без GET offset=0. После DOM render возвращают выбранную карточку на прежнюю высоту экрана и фокус на её ссылку с preventScroll. Anchor корректнее одного scrollY при смене ширины экрана; если anchor отсутствует, применяется сохранённый scrollY. B3 при открытии начинается сверху с фокусом на заголовке.
5. Native scroll restoration временно становится manual только в list/detail corridor, чтобы браузер не конкурировал с восстановлением до готовности DOM; вне него возвращается прежняя настройка. Пока восстанавливаем ленту, observer отключён. После восстановления он не подгружает новую порцию до действия пользователя (wheel/touchmove/scroll key или явная кнопка). Возврат не должен менять состав/позицию списка фоновым refresh.
6. Свежий переход в список из поиска, прямой URL, новая вкладка или полный reload без snapshot начинают с первой порции. В этих случаях восстановить прежнюю ленту при запрете persistence нельзя; пользователь видит вход/загрузку, а не фиктивно сохранённое место. Отдельный режим revalidation сохранённой ленты и виртуализация не входят в этот срез.

Основание API: Angular NavigationStart позволяет различить источник навигации, afterNextRender выполняет восстановление после render; IntersectionObserver реагирует на близость sentinel к viewport. [Angular navigation](https://angular.dev/api/router/NavigationStart), [render callback](https://angular.dev/api/core/afterNextRender), [IntersectionObserver](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API).

## Демо и доказательства

Локальный stub реализует тот же GET list shape и paging для созданных в нём вымышленных held/confirmed/ticketed заказов; список пуст до hold. Ответ детерминированно сортируется по `(bookedAt, aggregateId)`, не зависит от чтения single-order GET, не возвращает passenger data и отвергает Bearer header. После перезапуска stub заказы исчезают. Fake auth лишь позволяет пройти UX, не доказывает выдачу JWT, owner scope, replay идемпотентности, реальные payment/provider вызовы или работоспособность deployed issuer/Host. В demo browser-тесте разрешён ровно новый GET list путь через локальный proxy.

Проверка после отдельного согласования реализации: backend DB test owner isolation, tie-breaker, границы limit/offset; no-DB HTTP test auth, query binding и DTO; TS decoder/API client tests; Angular state, direct URL/OIDC, identity change, paging, stale response и projection-lag tests; Node demo stub tests и Playwright вымышленный путь с desktop/360px. Unit/no-DB проверки не заменяют live owner/projection acceptance. Реальный issuer callback path и deployed EF convergence остаются отдельными gates; их нельзя объявлять доказанными demo. Миграции, реальные интеграции и деплой не запускать.

## Критерии приёмки

1. Без валидного входа список не отдаёт карточки; сервер видит только owner GUID из проверенного JWT, чужие заказы отсутствуют в ответе и тестах.
2. Ноль, 1, 20, 21 и больше заказов отображаются без выдуманного `total`; автоматическая и ручная подгрузки дополняют ленту. Равные времена упорядочены детерминированно. Ограничение offset при одновременных изменениях явно принято.
3. Каждая видимая карточка ведёт на существующую B3-страницу; прямой URL списка и детали после reload проходят отдельный вход без PII/токенов в URL, storage или логах.
4. Empty/loading/401/403/network/timeout/malformed/недавняя запись различимы; поздний ответ другого owner/page не раскрывается. Автоматическое ожидание eventual projection ограничено абсолютными 30 секундами от hold: после deadline нет новых polling GET, текущий polling GET отменяется. При переходе к следующей порции ожидание и его сообщение завершаются. Сервис hint очищается при смене auth даже вне списка и не фабрикует заказ.
5. Демо изолировано на фиктивных данных; тесты проходят без реальных поставщиков, денег, Anthropic, применения миграций и деплоя.
6. После открытия заказа из ленты минимум 40 строк Browser Back и явная ссылка возвращают тот же выбранный заказ к прежней viewport координате (допуск 4px при неизменном viewport), восстанавливают фокус и не вызывают GET первой порции. После смены viewport anchor остаётся ориентиром; после logout/reload snapshot недоступен. Ошибка следующей порции сохраняет предыдущие строки.

## Самопроверка проекта

- Scope ограничен list UI, узкой сортировкой/`no-store`, auth return path, client decoder, owner-bound hint от hold и demo/test/docs. Cancel и новая backend запись исключены.
- У текущего API нет признака snapshot; вариант A и критерий приёмки прямо признают его ограничение.
- `BookedAt` в карточке назван временем hold; прямой URL без hint не обещает автоматического обнаружения невидимого заказа.
- Серверная owner-проверка и демо-имитация названы раздельно. Все решения сформулированы без неопределённых placeholders.
