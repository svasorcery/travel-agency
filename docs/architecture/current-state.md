Confirmation saves one financial attempt and minimal receipt evidence, without retrying capture or supplier payment after uncertainty. ## Data and messaging

A booking command applies the [typed Core transition](../../modules/flights/Travel.Modules.Flights.Core/Aggregates/BookingAggregate.cs), then the application writer commits the Marten event, a ReconcileOrderReadModel message and sibling notifications in one enrolled outbox. The [durable reconciler](../../modules/flights/Travel.Modules.Flights.Infrastructure/Persistence/OrderReadModelReconciler.cs) applies stream events after the persisted EF ProjectedStreamVersion. GET/List can briefly lag a successful command. Retry, dead-letter diagnostics, exclusive maintenance and rebuild/validation are described in [the recovery runbook](../operations/booking-read-model-recovery.md) and [ADR 0016](../adr/0016-booking-saga-via-marten-es.md). No mixed old projector is permitted.

[FlightsDbContext](../../modules/flights/Travel.Modules.Flights.Infrastructure/Persistence/FlightsDbContext.cs) owns the flights read model, idempotency and webhook inbox. [AiDbContext](../../apps/Travel.AI/Persistence/AiDbContext.cs) currently owns the AI cost ledger. Shared Infrastructure supplies ordered initialization primitives; Host and AI register actual initializers. Development/Testing apply checked-in schema changes before readiness; Production startup validates compatibility and does not apply migrations. See [ADR 0007](../adr/0007-storage-strategy-marten-ef-coexistence.md).

M2.2 introduced protected singular `OfferHeldV2`; M2.3b protects the complete validated party before `HoldOfferCommand` dispatch and emits `OfferHeldV3`. The purpose binds aggregate, owner, quote revision and count. State/owner/expiry/revision/count guards precede decryption; exact membership, details and age checks precede the single provider hold. Projection copies the exact opaque snapshot and recognizes V1/V2/V3 without keys. Ordinary Get/List selects no passenger column. The new `passenger_count` column defaults to one for historical orders; legacy plaintext history and rebuild representation remain unchanged.

New webhook inbox JSON contains encrypted original signed bytes plus bound routing metadata. Infrastructure decodes normalized booking facts; keyless diagnostics use metadata, while processing verifies its binding before acting. Missing keys never acknowledge an unprocessed event; existing bounded retry/DLQ applies. A dedicated certificate-protected filesystem Data Protection ring has no automatic empty-ring bootstrap and is separate from global authentication services. The early `flights-pii-keys initialize --execute` command registers no stores and starts no Host. Optional dependency health reports new-write availability, not historical decryptability. See [ADR 0024](../adr/0024-flights-pii-protection.md) and [operations](../operations/flights-pii-key-recovery.md).

Interactive NL-search sends the versioned [shared contract](../../shared/dotnet/Travel.IntegrationContracts.AI/NlSearch/NlSearchContracts.cs) through bounded Core NATS request/reply. [Travel.AI](../../apps/Travel.AI/Program.cs) registers AnthropicClient.AsIChatClient directly; it has no Microsoft Agent Framework or Semantic Kernel runtime. Wolverine/PostgreSQL supplies durable local queues and the booking outbox. JetStream availability on the broker does not make this NL-search request durable. [ADR 0020](../adr/0020-nl-search-cross-service-contract.md) owns that transport decision; [ADR 0012](../adr/0012-maf-as-primary-agent-runtime.md) defers a future MAF product milestone.

The [local README smoke](../../tools/docs/readme-smoke.mjs) exercises status, OpenAPI and invalid-search ProblemDetails through the running stack.

Health probes are on internal listeners: Host 5098 and AI 5159. Live means the process can answer; ready includes required own stores/schema/initialization; optional dependency health is diagnostic. Public health concealment and ProblemDetails are covered by [Host web tests](../../tests/Travel.Host.Tests.Integration/Web/HostWebContractTests.cs). The [Angular app](../../apps/web/src/app/) exposes anonymous Flights search/results and quote review, then an OIDC login, 1–9-adult hold/confirm flow, a list of the authenticated owner’s orders, and a one-order status page.

The Flights page submits the existing anonymous POST `/api/flights/search` only after form validation. It keeps actual offer currencies and backend order, displays bookable itinerary details, and presents Travelpayouts as a limited partner summary because its current mapper does not provide a complete round-trip or reliable transfer count. A bookable card can call anonymous `POST /api/flights/orders/quote`; the page compares the returned price and itinerary with the search result, shows old and new prices together, and asks for explicit acceptance of changes. The quote response includes fare facts already present on `BookableOffer`; baggage quantity is the mapper's maximum across segments, not a guarantee for each segment.

B2 uses the public `travel-web` Keycloak client with authorization code flow and PKCE S256 on local port 4200. Its access-token contract is `aud=travel-web`, a GUID `sub`, and `scope=flights:book`; the checked-in realm explicitly maps the audience and defines the Keycloak `basic` subject mapper because its custom default-scope list would otherwise omit `sub`. `keycloak-js` keeps tokens in memory. Outside local port 4200, the build requires a public `window.__TRAVEL_FLIGHTS_AUTH__` runtime config (`url`, `realm`, `clientId`, `environment: "staging" | "production"`) and HTTPS for both the app and issuer; no non-local issuer URL is embedded, so sign-in fails closed when config is missing. M2.2 removes the Travel sessionStorage booking draft: after redirect the page asks for fresh selection and quote, and deletes only its retired key without reading it. A same-page authenticated selection is still re-quoted before passenger entry. OIDC SDK protocol state is outside this Travel draft claim; the auth service/issuer contract is unchanged. Passenger PII and frozen attempts stay only in browser memory. Hold and confirm use separate UUIDv4 idempotency keys; M2.3a forbids another hold/confirm write after an unknown outcome, including after SPA navigation or a new search. Owner GET shows observed state and does not resolve the original attempt. Explicit logout/identity reset clears PII and invalidates stale completions; reload cannot recover the attempt. B5 cancellation retry remains separate and unchanged. Expected backend `ProblemDetails.type` codes distinguish expiry, in-flight retries, and unresolved booking conflicts. A successful confirm is labelled Confirmed, not Ticketed.

The `flights-demo` build has a build-time fake-auth service and fictional deterministic hold/confirm stub on port 4201; the stub refuses Authorization and does not echo passenger data. Its browser tests prove only demo UX. A separate local Keycloak 26.6.4 code-flow smoke checked the real access-token claims, and a no-database ASP.NET JwtBearer probe validated a real Keycloak token through the production claims transformation. These checks used the realm fixture and did not run Host/AppHost, a real supplier, payment, Anthropic, or migrations. The [local B2 report](../superpowers/results/2026-09-30-flights-m1-booking-b2-local.md) records commands and evidence boundaries.

B3 adds [`GET /api/flights/orders/{aggregateId}`](../../modules/flights/Travel.Modules.Flights.Api/Endpoints/GetOrderEndpoint.cs) to the typed frontend client and a Client-rendered `/flights/orders/:aggregateId` route. Successful hold and confirm responses are handed to this page in memory for the same owner; bounded polling tolerates a temporary owner-scoped 404 after either write, or stale `Held` after confirm, until the EF projection catches up. Direct links require re-login after reload because tokens remain in memory. The page displays Held without a fabricated deadline, distinguishes Confirmed from Ticketed, and shows ticket numbers only for Ticketed. Owner 404 on an unrelated direct URL stays unavailable with manual refresh but no automatic retry. The fictional demo adds deterministic delayed GET responses through Ticketed, without JWT validation or owner enforcement. Local source and browser evidence is recorded in the [B3 result](../superpowers/results/2026-09-30-flights-m1-booking-b3-local.md).

B4 exposes the Client-rendered [`/flights/orders`](../../apps/web/src/app/flights/flight-orders-page.component.ts) route through the typed `GET /api/flights/orders` client. The server derives the owner from the JWT; no client user ID is accepted for owner selection. Its read query filters by owner, sorts `BookedAt DESC, AggregateId DESC`, clamps limit to 1–200 and negative offset to zero, and returns `{items, limit, offset}` with `Cache-Control: no-store`. The server defaults remain 50/0; the [request catalog](../examples/flights-requests.json) uses the plain GET path and bearer header without extending its JSON schema for query parameters.

The list UI requests `limit=21` and displays batches of 20. It appends another batch automatically near the bottom, with **Показать ещё** as the manual action. Cards link to the existing B3 detail page and label `BookedAt` as the time the hold was created. The loaded orders, scroll position, and selected order survive the B3 round trip only in browser memory for the same owner. Reload clears the cache and requires re-login; logout or identity change clears owner-bound state. Tokens and passenger data are excluded from this cache, URLs, storage, and logs. The existing frontend `flights:book` login contract remains stricter than the authentication-only backend read routes.

Offset pagination supplies no total count or snapshot; concurrent inserts can shift later batches. Refresh restarts at offset zero. A recent owner-bound hold hint permits bounded waiting for eventual projection, without creating a synthetic order; a direct list reload has no such hint. The [demo server](../../tools/demo/flights-search-api.mjs) returns the same DTO shape from its in-memory fictional holds, starts empty, and resets on server restart. List reads are pure and do not advance the fictional B3 Confirmed-to-Ticketed scenario. It rejects Authorization headers and performs no JWT or owner enforcement. Node/demo-browser proof and no-database HTTP proof establish only their local boundaries; live issuer, real owner filtering with EF projection, supplier, payment, and ticket issuance acceptance remain separate gates.

These tests prove the stated source and local conditions only. A fake supplier is not a Duffel booking; a disposable Aspire stack is not a deployed environment. Paid Anthropic evals are separate from mandatory local checks. No production migration, shared-data cutover, external ingress or live customer delivery is established by this repository review.

## Flights M2.1 search ordering

The search Application uses deterministic `price-first-v1`: comparison within actual currency, then price, known full duration, duration, known transfers, transfers and a canonical tie-break. Requested currency is displayed first; FX failures retain their original currency and have separate group ranks. Partner duration/transfers remain unknown because current partner summaries are incomplete. This feature has no LLM dependency.

Search responses add optional `ranking` evidence; M2.3b introduced cache v3 and M2.5 advances normal-search cache to v4 below, preserving complete response facts and partial-provider status. Old cache keys expire naturally. Dedup retains different provider refs, purchase paths, fare terms, currencies and full itineraries. The UI preserves server order and explains factors through an accessible disclosure; it accepts legacy responses without inventing explanations. See the [M2 design](../superpowers/specs/2026-10-02-flights-m2-design.md) and [verification report](../superpowers/results/2026-10-02-flights-m2-ranking-local.md). Multi-passenger, saved travelers and ordered journeys are recorded below.


## Flights M2.3a booking correctness

The idempotency middleware bounds booking bodies to 16KiB in memory before hashing, model binding or dispatch; oversized requests return413 without store/provider effects. Raw request fingerprints remain unchanged. Quote acceptance and expiry are checked at the method boundary, including re-quotes after login.

Confirmation checks the supplier order and accepted amount/currency before the test wallet and before the payment POST. A matching succeeded receipt is required; 2xx alone is insufficient. Duffel POST never automatically retries. Possible hold dispatch failures and post-capture uncertainty return safe unknown errors; no false cancellation/refund/confirmation or automatic compensation is recorded. The success commit/outbox is unchanged.

No new events, read-model columns, migrations or recovery endpoints are introduced in A. External effects remain outside the commit and memory guards do not coordinate tabs or survive reload/restart. This is fictional demonstration correctness, not real payment acceptance. M2.3b extends this baseline below; M2.4 profiles and M2.5 ordered journeys are described below. See [M2.3 specification](../superpowers/specs/2026-10-03-flights-m23-design.md).


## Flights M2.3b passenger parties

Search accepts 1–9 adults; the legacy one-way/return request remains, and M2.5 adds ordered legs below. Duffel mapping requires matching adult references on every segment and records the first origin-local departure date and nullable hold/document capabilities. Travelpayouts groups are skipped before HTTP with explicit `skippedProviders`; skips are distinct from attempted-provider failures. Cache v3 introduced validation of these facts; v4 adds full journey and current capability inventory validation. Ranking still explains the actual whole-party total without paid AI.

A quote returns a fresh revision and local adult slots. An unchanged supplier reference set preserves local IDs and order; changed membership replaces them, and a count change requires a new search. The UI labels group totals and retains same-page form data only for the same owner and IDs while requiring fresh quote acceptance. Every row requires title, supported Latin name, DOB, explicit gender, email and phone. Adults turn18 using `DateOnly.AddYears(18)` at the stored departure date, including February29 to February28 in non-leap years. This is the fictional product convention, not a supplier/legal guarantee.

New holds require the latest binding and exact slot set. V1/V2 history remains replayable, and already-held legacy orders retain confirm/cancel behavior; old quoted streams need a new quote before hold. Read/list/cancel expose explicit count1–9 without names or ticket-to-passenger inference. The source-only `AddOrderPassengerCount` migration adds the default1 column and range check; offline Up/Down SQL was inspected, with no local database change. A rollback to old readers after V3 writes is unsupported; compatible schema/readers must precede activation. See [design](../superpowers/specs/2026-10-03-flights-m23-design.md) and [verification boundaries](../superpowers/results/2026-10-03-flights-m23b-local.md).


## Flights M2.4 private saved travelers

`/api/flights/travelers` and its GUID item route use JWT/`flights:book` and a synchronous Application service. EF owns `flights.saved_travelers`: ID, owner, revision, protected JSON, created/updated timestamps and owner/page index. No plaintext label/search index, profile events, booking foreign key or durable plaintext message. Separate Data Protection purpose binds owner/profile/revision and reuses the existing ring/certificates. All data remains fictional.

Create inserts a known client ID only; update/delete atomically match owner/ID/revision. Stale owned revision returns412; foreign/missing404; owner lookup precedes encryption. Delete needs no decrypt. GET/List filter owner before reading profiles, return at most20 items from21 opaque rows and fail closed on unreadable data. Writes expose only metadata receipts. The source migration adds only this table; Down would lose profiles if executed and leaves booking evidence intact. No local schema operation occurred.

Header-only module policy runs before authentication for profile `no-store` even on401/403; auth ordering remains. Body guards run after auth, reuse16KiB RAM reader and reject malformed/unknown/duplicate JSON before binder diagnostics can echo it. Booking fingerprints/idempotency remain; profiles never enter that cache. Real generated Wolverine handlers/metadata were tested with controlled services and no persistence/transport registration; full Host startup remains CI-only.

The client-rendered `/flights/travelers` UI explicitly copies seven details into one slot without changing its ID. Save DOB rules are separate from adulthood at travel. Owner/epoch/auth and quote/slot/selection/edit generations protect late results. Profile401/403 clears PII even without identity change; new owners get independent mutation gates. Unknown writes never retry automatically. Fresh GET supports current-state review and does not prove lost execution; profile uncertainty cannot release a booking barrier. Logout/identity/navigation erase memory. See [spec](../superpowers/specs/2026-10-03-flights-m24-saved-travelers-design.md) and [verification](../superpowers/results/2026-10-03-flights-m24-local.md).

## Flights M2.5 ordered legs and open-jaw

`SearchCriteria` owns immutable ordered legs and distinguishes legacy locations from explicit airports. Anonymous `/api/flights/search/v2` accepts 1–4 exact airport/date legs and 1–9 adults; old structured/NL contracts stay intact. Its scoped 16KiB in-memory guard rejects malformed, unknown and duplicate fields before binding, returning fixed errors without submitted values or dispatch. Explicit requested dates are nondecreasing; equal dates are allowed.

Fresh `Itinerary.Create` validates the nested graph and UTC chronology between legs. Connections stay inside slices. Slice duration remains less than 48 hours; the journey sum is less than 192 hours, excluding stays and independent ground travel. Duffel emits every requested leg and resolves each raw local timestamp against that airport's IANA zone through built-in `TimeZoneInfo`. Missing/unknown zones, DST gaps/offsetless overlaps or conflicting offsets fail safely. The first resolved origin-local date binds the passenger party/adulthood. A nonempty invalid response fails that provider instead of becoming empty inventory; quote maps the complete fresh offer with no earlier-search provenance claim.

Normal Redis search key/envelope v4 includes the full ordered request, route mode and sorted current provider capability inventory. Cold/warm validation covers route, cabin, count, first-local-date party binding, graph totals and provider/skip/failure identities. Adding/removing a configured provider changes the key even after all-success old results. V3 expires naturally; no flush or migration. Travelpayouts skips explicit journeys before HTTP with `journey-unsupported`, ahead of passenger-count rejection; legacy city and partner-summary semantics remain.

HTTP `journeyKind` is derived from geometry, including the flat historical DTO fallback. It is not an event/history version. Core JSON constructors and Apply retain stored instants/durations without fresh validation; malformed flat data remains rejected by the client contract path. Shared TS readers enforce consistent shape/kind across search, quote, list/detail/cancel, while fresh v2 checks are separate. One complete offer still produces one protected party and one order.

The UI adds a 2–4-row exact-airport form and shows all legs, connections, cabins and recorded airport offsets across result/quote/owned screens. Different adjacent airports produce an explicit independent-ground-travel notice. Any late-leg/cabin change requires acceptance even at the same price. Saved-profile slot/generation guards and unknown-write barriers remain; new search cannot release an unresolved booking write. Fictional acceptance covers open-jaw/four-leg orders for two saved adults, whole-order reads, late changes and mobile/keyboard behavior.

All four M2 product capabilities now have source implementations: explainable ranking, multi-passenger booking, private encrypted saved travelers and multi-leg/open-jaw. Privacy/booking correctness remains their foundation.
