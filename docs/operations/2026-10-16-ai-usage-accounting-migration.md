# AI usage accounting migration

Source migration `20261016091213_CostLedgerUsageOutcomes` extends the existing `ai.cost_ledger`: input/output token counts and cost become nullable; the required `outcome` column defaults to `LegacyRecorded`. Existing numbers, IDs, correlations and row count are preserved. Historical zero values may have come from missing usage, so this migration does not label historical billing as verified.

New NL-search work first commits an `Admitted` row with nullable usage/cost before model dispatch. If this admission cannot commit, no model call is made. Completion updates that same row to an explicit outcome such as `Ready`, `InvalidOutput`, `UsageUnknown`, `InferenceFailed`, `DeadlineExceeded` or `OutputBudgetExceeded`. If the final update fails, the committed `Admitted` row remains an explicit unknown outcome: it does not prove whether inference completed or what it cost. A process crash has the same uncertainty; observing an admitted row never authorizes replay.

Known usage is retained even when output is malformed or JSON null. Unknown/partial usage retains nulls and any known individual count; unknown cost remains null. A v1 successful reply still requires known usage and durable completion, uses the original message identity/shape, and carries the estimated standard-token cost. Unknown usage or accounting failure produces a safe failure/Host fallback. No model retry is added. The existing `(MessageIdentity,CorrelationId)` unique key rejects a competing admission before its model work; this is neither a response cache nor a general exactly-once guarantee.

The reviewed Up SQL uses `DROP NOT NULL` on three columns and adds `outcome text NOT NULL DEFAULT 'LegacyRecorded'`; it updates no historical token/cost values. EF applies the schema/history transaction atomically. PostgreSQL locks the table during DDL; assess table size and active transactions in the separately approved deployment window.

Deploy the source migration before admitting the updated AI process. Production initialization closes messaging startup while it is pending. Drain old AI writers/readers before the switch: an older non-nullable EF reader cannot consume new unknown-usage rows. Old inserts that omit outcome receive `LegacyRecorded`, which does not claim newly verified accounting. This is a source/disposable-test compatibility decision, not evidence of a target migration or live deployment.

Down first takes an explicit `ACCESS EXCLUSIVE` table lock within the migration transaction, then refuses if any token/cost is null or any outcome is not `LegacyRecorded`. Holding this lock through the guard and DDL prevents a concurrent new writer from inserting a non-null outcome between validation and dropping the column. Removing the outcome column or replacing unknown values with zero would destroy retained accounting evidence. Keep the current schema/application or arrange a separately reviewed preservation/restore procedure; do not delete ledger rows to force rollback. When only historical rows remain, Down removes the added outcome and restores the former NOT NULL constraints without numeric substitution.

Offline review artifacts are generated under ignored `TestResults/technical-audit-remediation-2026-10-16/ai-usage-up.sql` and `ai-usage-down.sql`. `CostLedgerUsageMigrationTests` verifies historical numeric preservation and guarded rollback against disposable PostgreSQL. No live database application, model call or billing inspection is part of this change.
