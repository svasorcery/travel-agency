# Rail module

Rail M1/M2 have a default-off read-only source implementation for Yandex.Rasp station selection and direct train/suburban schedules, local ordering/filters, explicit bounded route details, independent optional ticket facts and exact prices. Core/Application/Infrastructure/Api remain separate; Application owns normalized ports, Infrastructure owns wire parsing and provider HTTP.

The repository is an OSS/demo project; source-only publication and fictional demos do not require a public deployment or real credentials. Each operator who chooses real access brings their own account/key and remains responsible for provider terms, quotas, data use and attribution. Existing real-source gates apply to that chosen deployment, not as unfinished source tasks. See README.md#ossdemo-and-optional-real-access. Documentation of opt-in access grants no authority to register, call providers, enable or deploy.

DB/GTFS, multiple sources, inventory and booking remain future scope. Only temporary bounded RAM data is used; there is no persistence/migration. Current contracts are ../../openspec/specs/rail-schedule-search/spec.md and ../../openspec/specs/rail-journey-details/spec.md. M1 retains all25completed tasks/evidence in ../../openspec/changes/archive/2026-10-20-rail-m1-yandex-search; M2 retains all21completed tasks/reviews and PR64/CI receipts in ../../openspec/changes/archive/2026-10-22-rail-m2-journey-selection-details. See README.md and ../../docs/architecture/rail-completion-review.md for acceptance and pending external gates.

Host imports the implemented Api.Composition facade only. Real source access remains default-off, startup does not call suppliers, fictional transport is explicitly selected and cannot replace a real failure. Source/local, actual isolated Host/OpenAPI, the fixed fictional measured profile and ordinary PR/post-merge CI are accepted. Real source/banner and target rollout still require separate acceptance/authorization. Other module composition belongs to its own facade.
