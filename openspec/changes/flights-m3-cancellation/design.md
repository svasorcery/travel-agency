# Flights M3 cancellation — проект дизайна

**Статус 2026-10-05:** D1–D8/вариант A и E1–E6 определяют согласованный полный план. T1–T2 tooling и full authenticated verifier PASS; T3–T5 завершены, T6 выполняется; source migrations/delivery не выполнялись. Требования — соседний OpenSpec spec, единственный execution plan — tasks.md. Tooling acceptance не подтверждает supplier cancellation или durable product behavior.

## Результат и варианты

Согласие привязано к конкретным текущим условиям целого заказа. После сбоя система устанавливает факт из поставщика или сохраняет unknown/manual; пользователь не должен угадывать по устаревшему GET, повторять опасную команду или восстанавливать ключ из browser storage.

| Вариант | Сильные стороны | Цена и слабые стороны |
| --- | --- | --- |
| **A. Cancellation substate внутри BookingAggregate stream — рекомендуется** | Один authoritative booking write boundary; operation/consent/confirm barrier конкурируют через stream version; использует existing Marten/Wolverine atomic outbox и versioned reconcile. | Больше событий booking; новые readers/projector должны понимать добавленные facts; нужен аккуратный stage reducer и ограниченное изменение ConfirmOrderHandler. |
| B. Отдельный cancellation document в Marten | Operation history отдельно и удобна для самостоятельных queries. | Atomic document+stream gate/transaction и совместная проверка writers сложнее; без неё возникает два конкурирующих источника. Потребуется обосновать изменение ADR0016, не новый универсальный Saga. |
| C. EF operation/outbox плюс Marten booking | Удобная SQL модель operation. | Ещё один write authority и разрыв EF→Marten; сложнее recovery и fencing. Для этого пилота цена не оправдана. |

Только память/HTTP idempotency исключены как вариант: они не достигают требуемого reload/restart результата.

## Принятые бизнес-решения D1–D8

| ID | Предложение | Альтернатива/последствие |
| --- | --- | --- |
| D1 | Held/Confirmed/**Ticketed** при актуальном supplier available_actions и отсутствии competing effect. | Сохранить B5 Held/Confirmed: пилот уже, Ticketed UI остаётся unavailable. Выбран первый вариант по approval пользователя. |
| D2 | Принимать известный refund ≥0 в supplier currency и поддержанный monetary destination; zero показывать явно. awaiting_payment только при проверенном unpaid/zero. Unknown amount/currency/expiry, credits/vouchers/mixed settlement → manual без confirm. | Полноценные credits/unknown-amount consent расширяют UI/PII/financial модель; отдельное развитие. Не заменять null нулём. |
| D3 | Согласие на immutable local revision, supplier cancellation ID/order, amount, currency, destination, expiry, scope/route/party и versioned notice. Изменение любого meaningful fact требует нового explicit consent. | Amount-only consent не защищает от валюты, назначения, срока или другого cancellation ID. |
| D4 | Unknown удерживает mutation barrier; только bounded read recovery. Timeout/длительная неизвестность → ручная проверка, без auto-confirm retry. | Supplier-side retry позже возможен только после независимого подтверждения его контракта. |
| D5 | Бounded server barrier распространяется на existing confirm pre-dispatch; неизвестный confirm блокирует cancellation. Автоматическое восстановление платежа не включаем. | Если менять confirm нельзя, отмена Held не имеет честной cross-client гарантии; тогда scope сузить/пересогласовать, не обещать её. |
| D6 | Supplier cancellation success даёт Cancelled; отдельный supplier refund evidence не устанавливает CustomerPaid/старый Refunded из booking total. | Reuse OrderRefunded смешивает существующий airline callback и денежную выплату. Нужен отдельный расширенный money cycle. |
| D7 | Явный ManualReviewRequired с owned UI и ограниченной operator resolution, typed outcome + safe evidence reference + actor/time/revision. Без Support subsystem/свободного PII текста. | Только ссылка «обратитесь» без пути фиксации результата не завершает recovery. Предлагаемый operator scope `flights:cancellation-review` + валидный GUID subject и обычная JWT audience validation; Контракт resolver конкретизирован в E1–E4 ниже. Реальное назначение scope/realm provisioning не входит в эту работу. |
| D8 | Новый consent protocol; старый bodyless cancel запрещает новую supplier mutation и сохраняет terminal owned no-op. | Молчаливое изменение старого POST нарушит клиентов и consent; compatibility rewrite не допускается. |

Все восемь решений, включая bounded confirm coordination, составляют принятую основу плана. Approval планирования не разрешает платежи клиенту, реальные suppliers, установку, product execution или deployment. История предыдущих approval вопросов сохраняется только в review/process-log.

## Authoritative модель и границы слоёв

Core владеет immutable CancellationTerms, typed stage/outcome/evidence и cancellation substate в BookingAggregate. Fact events в past tense реализуют IDomainEvent; ErrorOr factories и TimeProvider в production. Старые V1/V2/V3 identities/JSON/Apply остаются неизменными; новые Apply также pure replay, present-day supplier проверки только в write decisions.

Application выполняет: owned prepare, consent, dispatch, observe/finalize, manual resolution. Infrastructure реализует `DuffelFlightCancellationProvider` за provider-neutral capability (например, `IFlightCancellationProvider`); wire DTO/parser/raw refund_to mapping живут только там. API endpoints вызывают Application, Composition регистрирует module handlers и local durability; Host global builders/security/endpoint mapping сохраняются.

Operation хранит: client-created UUID operation ID, booking/owner, phase, monotonic revision, immutable terms revision/hash, supplier order/cancellation reference, accepted-at/notice version, observation provenance/time, dispatch claim, attempt count/next-read deadline, safe reason/outcome, confirmed booking stream version. Ни пассажирской PII, токенов, provider response body, voucher codes, ни payment secrets не нужно. GUID operation не является authorization.

Предложенные semantic events (названия уточняются при approved implementation plan): CancellationPreparationStarted, CancellationTermsObtained, CancellationTermsAccepted, CancellationConfirmationDispatched, CancellationOutcomeBecameUnknown, CancellationSucceeded, CancellationRejected, CancellationManualReviewRequired, BookingOperationReviewRecorded; плюс bounded confirmation barrier facts. Связанный OrderCancelled добавляется **один раз** в том же terminal commit. История не переписывается; legacy Refunded остаётся legacy fact без выдачи его за M3 receipt.

### Monetary-only evidence predicates

Capability возвращает нормализованную SettlementComposition: CashOnly / Unpaid / CreditOnly / Mixed / Unknown, с provenance; это не raw enum refund_to. Mapper обязан прочитать и проверить наличие/shape `airline_credits`, различать explicit empty list и missing/null; любые credits, malformed/unknown destination или unknown composition не допускают auto-confirm. Monetary destination whitelist: balance/card/arc_bsp_cash; awaiting_payment только при positive unpaid/zero + no credit facts. `original_form_of_payment` допускается только с независимым affirmative CashOnly proof исходной supplier оплаты и empty credits; иначе Unknown/manual. Numeric refund_amount плюс refund_to недостаточны. Положительное число в mixed void может включать cash и reissued credit и не называется денежным возвратом.

База Travel не сохраняет достаточное supplier original-payment composition evidence; internal PaymentAuthorized не доказывает cash-only settlement. Поэтому исторические `original_form_of_payment` без trustworthy payment provenance остаются manual. Source guide listing order payments содержит not-yet-available caveat: не предполагаем доступность этого endpoint и не добавляем его как обязательный рабочий recovery API. Будущий adapter обязан доказать positive mapping поддержанного cash-only случая, либо честно остаться unsupported для него. Tests: original_form_of_payment+nonempty credits, numeric grand total mixed, missing/null/invalid credits list, неизвестный enum, CashOnly без provenance, unpaid при confirmation uncertainty, direct monetary destination и explicit empty credits, consent-bound composition/destination изменения.

## Lifecycle и crash boundaries

```text
Preparing -> TermsReady -> Accepted -> DispatchClaimed -> Succeeded | Rejected | Unknown
     |            |           |              |                       |
   Unknown     Expired/      stale          crash                  bounded reads
  /manual      Superseded   refusal        ->Unknown             ->manual review
```

Фазы и бизнес-исходы разделены: Accepted/DispatchClaimed не являются успехом. Preparation unknown не означает неизвестную **отмену**: supplier create не подтверждает её, и consent ещё не принят.

1. **Prepare admission:** Core owner/state/current-operation/confirmation-barrier check; optimistic commit PreparationStarted и durable local work до network. Два разных operation IDs для одного booking конкурируют на одной версии. Lose → no network.
2. **Read eligibility/create terms:** fresh supplier observation, identity/current capability/unpaid evidence. Supplier mutation create вызывается только после сохранённого claim. Response с id/terms сохраняется новой authoritative транзакцией. Потерянный create → read-only discovery; не коррелировать newest/amount/time heuristics. Не найдено достоверного кандидата → preparation manual/unknown. Повтор prepare не выполняет второй create автоматически.
3. **Terms/consent:** UI показывает entire persisted scope/route/group, amount/currency/destination/expiry и «возврат поставщика не означает выплату вам». Consent POST body operation ID + exact terms revision/hash + explicit accepted notice; auth owner проверяется заново. CAS решает конкуренцию refresh/consent; stale/expired terms не dispatch. Получение нового supplier quote никогда не наследует consent.
4. **Dispatch admission:** durable Accepted + work message атомарны. Fresh worker проверяет persisted consent, TimeProvider expiry, latest local revision и supplier terms identity/current order. Изменённый/заменённый quote → refusal requiring new consent до mutation. Supplier latest правило защищает от внешнего quote race; atomic precondition на amount не предполагается. При возможной in-place mutable terms без supplier гарантии — остановить adapter acceptance, объяснить limitation, не компенсировать молча.
5. **Single dispatch claim:** ожидаемая booking/operation revision атомарно фиксирует возможность отправки. Только победитель вправе вызвать confirm. Redelivery/restart не отправляет claim повторно. Crash после claim **до send** может оставить unknown даже без внешнего эффекта: без supplier idempotency это сознательная safety/liveness цена. Timeout lease не даёт разрешения новым POST; late original worker остаётся возможным.
6. **Result:** валидный matching confirmed cancellation → append Succeeded, OrderCancelled если ещё не terminal, supplier evidence и reconcile/notification atomically. Нет EF query для определения успеха. Локальный conflict/save failure после external success → новая read recovery, не новый mutation и не Rejected. Подтверждённый refusal допустим только для известного первого dispatch, где доказано отсутствие действия; response generic 4xx/500/503 не достаточен. После прежней unknown поздний refusal не снимает барьер.
7. **Restart/visibility:** один commit каждого возможного supplier dispatch заранее сохраняет фиксированный набор scheduled observation messages и deadline message в enrolled Marten outbox. Wolverine восстанавливает их из своего message store; scan booking streams не требуется. После исчерпания budget manual сохраняет correlation facts и mutation barrier. Точный контракт ниже, «Durable recovery без scan».

Operation ID создаётся клиентом до prepare; после lost prepare response/reload owned order cancellation-read находит серверную operation. Browser storage/URL для key/operation/terms не требуется. Существующий aggregate GUID route разрешён только как уже принятый order locator; supplier/operation IDs туда не помещаются.

До consent известная завершённая подготовка TermsReady или UnsupportedTerms может быть явно оставлена пользователем; TermsReady может также истечь: CAS закрывает review и освобождает admission только если dispatch невозможен и нет ещё выполняющегося create. Consent/abandon/expiry race имеет одного победителя; старый consent после закрытия невалиден. Accepted/DispatchClaimed/Unknown/ManualReviewRequired нельзя abandon/expiry разблокировать. Preparation с потерянным ответом или незавершённым worker нельзя автоматически пересоздавать по таймеру. Для первого transport добавить POST `/api/flights/cancellations/abandon` с aggregateId/operationId/expectedRevision, без supplier mutation; event CancellationReviewWasAbandoned. Это закрытие review, не успешная отмена booking.

## Конкурентность и existing confirmation

Одного optimistic commit **после** provider недостаточно. Новый confirm writer до wallet/provider effect должен сохранять bounded ConfirmationStarted gate в том же stream, и проверять отсутствие active cancellation; cancellation также проверяет его. Сохранённый admission winner определяет единственное действие. До side effect гарантированный preflight refusal может освободить gate; после возможного effect unknown удерживает его. Success commit сохраняет existing PaymentAuthorized/OrderConfirmed semantics и освобождает gate атомарно; save conflict после эффекта не делает gate safe-to-retry.

GET cancellation-status должен возвращать отдельный owned blockingConfirmation summary даже при отсутствии cancellation operation: phase/attempt identity/revision, unknown/manual reason и путь проверки. Crash после ConfirmationStarted до wallet/provider — обязательный сценарий; отсутствие cancellation operation не означает отсутствие blocker. Manual lifecycle confirmation barrier определён в E2 ниже: до EffectsClaim — CAS close; после возможного effect — только проверенное завершение либо сохранённый manual block. Silent clear/payment retry отсутствуют. Это координация и честное блокирование existing confirm, не новая payment recovery реализация. Historical Held без marker не доказывает, что предыдущий процесс не имел unresolved capture. При будущей активации M3 нужны drained old writers и отдельно доказанный безопасный baseline для legacy Held; неоднозначные исторические операции manual. Никакого online backfill или ledger inference из GET. Этот rollout gate записывается, но deploy сейчас не выполняется.

Ticket/airline callbacks не блокируются как входящие факты. Они используют свежий aggregate decision и CAS, инвалидируют непосланные stale terms при meaningful change. После dispatch внешний matching success должен быть зафиксирован даже если Ticketed event успел прийти; нельзя отклонить доказательство только по обычному B5 DecideCancel. Если airline cancellation уже сделала Refunded, сохранить собственное operation evidence без второго OrderCancelled/notification и без изменения старых денежных данных. Order cancelled другим действием: показать факт заказа отдельно, наша операция остаётся unknown/manual пока correlation не доказана.

## Recovery, manual и UI

Evidence ladder: (1) matching cancellation GET confirmed_at with identical accepted terms; (2) matching order.cancellation object; (3) cancelled_at-only — order fact, не operation/financial success; (4) empty/pending/missing/error — unknown. Для terminal rejection требуется affirmative evidence, а не отсутствие успеха. Known order cancelled + differing terms/cancellation ID → manual provenance review, не наша success.

### Durable recovery без scan — исправление PR2

Выбран фиксированный durable schedule на **каждый возможный mutation dispatch**, а не поиск по всем booking streams. Источник незавершённой работы — persisted Wolverine envelopes; booking stream остаётся authoritative источником operation state. Новая operation table, active-operation projection/index, polling hosted service и periodic aggregate replay не входят в этот вариант. Existing live projection и BookingStreamCatalog не используются для online recovery discovery.

| Граница | Один атомарный Marten commit до следующего действия | Поведение после restart/duplicate |
| --- | --- | --- |
| Prepare admission | PreparationStarted + ExecuteCancellationPreparation + AdmissionDeadline due admittedAt+310s | Durable delivery возобновляет admission; deadline переводит ещё не claimed стадию в manual, не объявляя cancellation outcome. |
| Consent admission | TermsAccepted + ExecuteCancellationConfirmation + AdmissionDeadline due acceptedAt+310s | Те же правила; наличие consent не даёт права повторного supplier POST. |
| Create/confirm dispatch claim | Immutable recoveryEpoch/dispatch timestamp + четыре ObserveCancellation(epoch,slot) + RecoveryDeadline(epoch) | Только winning claim sender может отправить один POST. Остальные deliveries не отправляют mutation; scheduled reads уже существуют независимо от acknowledgement sender. |
| Получен валидный результат | Observation/outcome facts + при необходимости OrderCancelled + reconcile/notifications | Сохранённый результат монотонен; оставшиеся wakeups заканчиваются no-op. Losing transaction не публикует свои messages. |

Для каждого claim `t0 = TimeProvider.GetUtcNow()` сохраняется в событии один раз. Четыре observation slots имеют абсолютные due times `t0+2s`, `t0+10s`, `t0+60s`, `t0+300s`; deadline — `t0+310s`. **Все пять envelopes записываются с claim**, не после HTTP и не цепочкой после ответа предыдущего reader. Для pre-consent create и consented confirm epochs различны; budget относится к конкретному claim, не сбрасывается retry/restart/GET. В одной operation допускается не более одного create и одного confirm claim. Новые terms после закрытого review — новый explicit prepare/operation, никогда замена неизвестного effect.

Каждый admission commit сохраняет immutable admissionId, actionStage (Prepare или Confirm) и admittedAt; соответствующий AdmissionDeadline несёт operationId/admissionId/actionStage. Consumer проверяет именно эту admission identity, её pending phase и отсутствие claim, а CAS выполняет по **свежезагруженной** booking/operation revision. Исходный revision не является условием действия watchdog: harmless progress или чужое nonterminal event не отключает deadline. Watchdog подготовки не может примениться к более позднему consent admission той же operation. Если matching claim уже записан, этот watchdog no-op: работает recovery deadline соответствующего claim. Если deadline выиграл CAS до claim, старый executor больше не может получить admission на mutation. Это manual/blocked с доказанным locally-not-dispatched фактом, а не provider rejection; снятие barrier требует отдельного разрешённого решения. Никакой expired lease не разрешает новый POST.

ObserveCancellation открывает свежий stream, проверяет operation+epoch, stage и deadline, затем **до GET** через CAS записывает расход данного slot. На epoch хранится монотонная маска четырёх потраченных slots; повтор одного slot/проигравший CAS не делает нового logical observation. Crash после расхода slot до GET расходует эту попытку: следующие slots и deadline уже durable. Если накопились просроченные сообщения, один CAS расходует их вместе и разрешает только самый поздний due slot; устаревшие сообщения no-op. На epoch допускается не более одного действующего read-window. Если очередной due slot пришёл при ещё открытом 10s window, CAS расходует этот slot без GET; повторно он не планируется, оставшиеся slots и deadline уже durable. Успешная запись observation закрывает window раньше срока. После истечения window late reader может ещё вернуть ответ, но имеет только GET, не mutation; matching late positive evidence принимается свежим CAS. Budget задаёт максимум четырёх logical reads, а не обязательное выполнение всех четырёх.

Один round имеет общий 10s cancellation budget и ограниченное число read endpoints; adapter заранее фиксирует это в contract tests. Внутренние GET retries Duffel ограничены существующей resilience policy и тем же общим deadline; **четыре slots — logical observations, не обещание четырёх wire requests**. Unknown create без достоверной supplier correlation можно закончить ManualReviewRequired раньше; не создавать новый cancellation quote для «проверки». Никаких запросов после deadline из автоматического recovery. Deadline-handler при неустановленном результате атомарно пишет ManualReviewRequired и сохраняет mutation barrier. Позднее matching success допускает finalization из manual/unknown через свежий CAS; поздний error/pending не стирает известное success.

Реализация использует `IMartenOutbox.Enroll(session)` и `PublishAsync(message, DeliveryOptions { ScheduledTime = dueUtc })` с module-owned durable local route `flights-cancellation`; process-global builders/policy остаются Host-owned. `DeliverWithin`/TTL-drop для recovery envelopes не задаётся. Helper должен принимать и регистрировать **все** work messages до единственного SaveChanges, вместе с обычным reconcile/notifications; plain bus.ScheduleAsync после commit не считается atomic substitute. При failure до commit не должно быть supplier POST; после claim commit recovery envelope уже сохранён. Сигнатуры ScheduledTime/Enroll подтверждены локальными XML installed Wolverine 6.17.0; фактическая atomic scheduled-outbox связь требует нового existing-CI integration proof.

Transport storage retries/DLQ не означают business outcome. Для этих новых типов module policy задаёт storage retry 1s/5s/30s → durable DLQ; terminal source/binding errors сразу в DLQ и безопасную диагностику. После восстановления storage Wolverine возобновляет persisted envelopes. При exhausted/terminal delivery оператор видит exact pending/DLQ evidence и может повторно поставить **только safe ObserveCancellation/AdmissionDeadline/RecoveryDeadline envelopes**; replay не меняет epoch/budget и не вызывает mutation. Отдельного reconciliation scan для этого нет. Текущее maintenance whitelist следует явно расширить этими safe типами, с тестом отказа для ExecuteCancellation* и HTTP booking commands. Если storage недоступен, система не утверждает, что manual-status уже записан: сохраняются последний факт и delivery diagnostic; подтверждённый business result появляется только после успешного commit.

Owned «проверить результат» вызывает read-only observation с rate limit; не создаёт epoch, не восстанавливает потраченный automatic budget и не снимает barrier само по себе. Его success finalization использует те же evidence/CAS predicates. Пользовательский rate limit и operator transport определены в E1/E3 ниже; источник restart discovery, automatic budget и crash boundaries также фиксированы.

Обязательный CI proof до UI acceptance: admission/claim rollback не публикует envelopes; persisted claim содержит все 5 scheduled messages; crash после commit до HTTP, после provider success до save и после read-slot reserve до GET; restart без republish/client GET; competing recovery workers/duplicate/overdue deliveries и skipped slot при активном read-window; admission deadline после harmless revision advance и запоздалый Prepare watchdog при Confirm admission; deadline после всех потерянных read responses; storage retry/exhaustion/DLQ replay; late positive response после manual; ни один сценарий не делает второй supplier POST. Existing BookingProjectionDeliveryTests подтверждает паттерн persisted scheduled envelope/new host, но не считается готовым M3 proof. Реальные fixtures только в существующем CI.

Manual resolution требует отдельного утверждённого operator permission, CAS exact operation revision, evidence category/reference и actor/time. Клиент не может объявить себя оператором, прислать supplier JSON или status override. Before negative resolution/unblock необходимо подтвердить, что старый dispatch worker больше не может послать запрос, и получить положительное доказательство отказа/отсутствия операции. Elapsed timeout/lease/GET pending этого не доказывают. Без достаточного evidence manual сохраняется; поддерживается повторное чтение/добавление проверенных фактов, но не «force success».

Предложенные neutral HTTP shapes: POST `/api/flights/cancellations/prepare` body aggregateId/operationId; POST `/api/flights/cancellations/consent` body aggregateId/operationId/termsRevision/termsHash/accepted; GET `/api/flights/orders/{aggregateId}/cancellation` owned authoritative snapshot, no-store. Exact repeat stage/body returns same operation, payload/identity mismatch conflict. Эти маршруты не наследуют старый EF response cache middleware; durable operation protocol обеспечивает own dedup, без PII request body. Истечение старой 24h HTTP replay не разрешает повторный effect. Операторский transport/permission и точные новые request/response shapes определены в E1/E3 ниже; эта краткая схема не переопределяет их поля.

Reload/auth return сначала read; никогда auto-consent/confirm. Logout/owner switch скрывает data и invalidates callbacks. Same-owner token refresh не меняет operation. Auth expiry после принятия сервером не отменяет durable work; последующее чтение снова требует authorization. Application access/export/observability не помещают клиентские operation IDs/keys/consent, PII, токены и raw supplier responses в URL/history/browser storage/logs; diagnostics используют safe категории/счётчики, evidence хранится только в разрешённой серверной модели. Operation revision/version и owner epoch фильтруют поздние ответы; stale EF order/read feed не откатывает authoritative success. UI отдельно показывает projection synchronizing, unknown/manual и supplier refund information. Whole party/все legs показаны; никакой partial cancellation.

## Совместимость, безопасность и проверка

Новые operation events не содержат raw provider payload/PII; новые projector cases сохраняют version checkpoints и historical V1/V2/V3 data. Initial design не требует новой EF operation table; source migration нужна только если утверждённый UI/projection контракт потребует дополнительные SQL поля. Не создавать/apply migration автоматически. Старые unknown event readers не являются безопасным rollback: сначала совместимые readers, потом writers; future rollout отдельный gate.

Local verification после approval: pure domain/stage and parser tests, audited no-DB HTTP, WireMock loopback, TS/Angular, isolated fictional Node/Playwright, .NET build последовательный. Real durable restart/Marten/outbox/projection tests обязательно в существующем CI. До запуска fixture аудит schema init; текущий CancelOrderHandlerTests локально запрещён. Paid evals skipped, backend auth/PII rules неизменны. Tooling plan/tests отдельно в harness-integration, costs/review в process-log/review.

Основной риск не OpenSpec syntax, а доказуемая supplier correlation и single-dispatch liveness. Если реальный контракт не позволяет установить исход, bounded manual является результатом, а не скрытым workaround. Runtime supplier acceptance не обещана и не выполнена.






## Окончательные технические решения E1–E6

Эти решения закрывают прежние planning gaps. Их ограничения являются частью выбранного поведения, а не задачами «решить позже». Runtime соответствие проверяется задачами/тестами, не предполагается из текста.

### E1. Manual review: отдельный HTTP boundary и явное происхождение решения

Добавить policy `flights:cancellation-review`: обычная JWT signature/issuer/audience/lifetime validation, normalized scope и непустой GUID sub. Это отдельная привилегия оператора; `flights:book` её не заменяет. Actor берётся только из проверенного principal. Realm/scope assignment не выполняются этой задачей. Тесты используют подписанные fictional JWT и реальный validator в изолированном no-DB TestServer; никаких production fake-auth путей.

Operator API: `GET /api/flights/orders/{aggregateId}/cancellation-review` и `POST /api/flights/cancellations/review/resolve`. Первый возвращает metadata operation/confirmation blocker/evidence без passenger PII/сырых ответов; второй принимает bounded typed decision из таблицы. У operator scope допустим review чужого owned order; обычный owner GET по-прежнему owner-only. Ownerless history не приобретает владельца через resolver.

Resolve body: aggregateId, targetKind (`Cancellation`/`Confirmation`/`LegacyHeld`), targetId, expectedRevision, resolutionId, decision, evidence. Для LegacyHeld targetId=aggregateId и expectedRevision=текущий booking stream version; для остальных targetId=operationId/confirmationAttemptId и revision=их собственная revision. UUID не пусты; revision>0; body<=16KiB; enum/string duplicate/unknown properties invalid. `resolutionId` связывается с target+actor+нормализованным payload hash и сохраняется в событии: exact retry возвращает текущий authoritative результат без повторного event/notification; изменённый body с тем же ID —409. Actor/resolutionRecordedAt/bookingStatus не принимаются из body; evidenceObservedAt и stoppedAt допускаются только как проверяемые поля evidence, не как время аудита. Чтение и ответы no-store, request/response bodies/operation/evidence refs не логируются.

Evidence допускает только классифицированные facts и opaque ссылки: `evidenceRef` и `quiescenceRef` — `[A-Z0-9][A-Z0-9-]{7,63}`, без URL/свободного текста/вложений; supplierOrderId/cancellationId сверяются с серверной binding, а не выбирают target. Если supplier receiptRef уже сохранён, нужен exact match. При потерянном payment response ConfirmBooking может ввести ранее неизвестный receiptRef только как OperatorVerified evidence: exact persisted attempt/providerOrderId/acceptedMoney/saved PaymentRef + trusted correlation attestation. Сохранённый ref не заменяется, а отсутствие saved PaymentRef не лечится вводом нового произвольного wallet ref: такой случай остаётся inconclusive. Raw supplier JSON, credit codes, имена/контакты не принимаются. EvidenceObservedAt<=serverNow. Для negative post-dispatch judgement observedAt должен быть после recorded stoppedAt и не старше15 минут. Срок15 минут — product convention для review свежести, не гарантия supplier консистентности.

| Decision | Минимальные достаточные факты | Result |
| --- | --- | --- |
| RecordInconclusive | Operator scope, exact target/revision, valid evidenceRef/category | ManualReviewRequired остаётся; provenance добавляется, barrier не снимается. |
| CloseNotDispatched | Authoritative stream показывает admission без Effects/Dispatch claim; CAS закрывает именно этот admission, active writer никогда не имел права на side effect | Attempt закрыт как NotDispatched, последний booking status сохраняется. Это не provider rejection и не успешная отмена. |
| ConfirmCancellation | Согласованные terms уже существуют; exact accepted cancellation ID/order, подтверждённый timestamp и matching amount/currency/destination/scope. Источник — сохранённая валидная API observation либо явное operator supplier-support attestation | Succeeded + OrderCancelled/evidence atomically, с ResolutionSource=SupplierApi или OperatorVerified. Клиентская выплата не устанавливается. |
| ConfirmNoEffect | Для данного possible dispatch supplier/support **положительно** подтвердил окончательное отсутствие исполнения и оставшихся pending requests; есть проверка остановки sender по E4. Null/pending/404 недостаточны | OperatorVerifiedRejected; barrier снимается только этим новым CAS commit. Предыдущая uncertainty остаётся в истории. |
| EnableLegacyCoordination | Только LegacyHeld binding и positive legacy drain/no-effects evidence по E4 | Append coordination marker+operator audit, без смены BookingStatus/owner. |
| ConfirmBooking | Только для confirmation target: отдельные positive wallet capture и supplier payment/order facts с exact accepted amount/currency/order и сохранённым PaymentRef; old sender quiesced, если он мог продолжать chain | Existing PaymentAuthorized/OrderConfirmed + ConfirmationAttemptCompleted атомарно; отсутствующая wallet evidence не синтезируется из supplier status. |

Для неизвестной Preparation без consent `ConfirmCancellation` запрещён. Если quote creation завершился, оператор может привязать **проверенный именно для этого dispatch** supplier quote и перевести в TermsReady; это отдельное decision `ConfirmPreparedTerms`, без наследования consent. Иначе RecordInconclusive или ConfirmNoEffect с E4; новый prepare разрешён только после доказанного закрытия прежней возможной mutation.

Система проверяет authorization, identity, обязательность/формат facts, соответствие сохранённым terms и допустимость transition. **Supplier-support и infrastructure quiescence attestations являются явно доверенным суждением уполномоченного оператора, не машинной/криптографической проверкой внешней системы.** UI и аудит сохраняют `OperatorVerified`, actor/time/evidenceRef; не называют это API receipt. Источник подтверждения нельзя подменить. Если оператор не располагает достаточными facts, разрешён RecordInconclusive и operation остаётся blocked без срока автоматического снятия. Это полностью определённый supported результат пилота.

### E2. Confirmation barrier: конечный lifecycle без payment recovery engine

Новые Held orders получают `BookingMutationCoordinationEnabled` в том же commit, что OfferHeldV3. Это marker протокола writers, не новая версия passenger history. Для legacy Held без marker новый confirm/cancel fail closed с `LegacyConfirmationUnverified`; operator может добавить marker только через LegacyHeld review с отдельной legacy-веткой E4 и positive no-payment-effect evidence. Автоматического backfill нет. Existing Confirmed/Ticketed и исторические readers сохраняются; provider settlement evidence всё равно проверяется по D2.

`ConfirmOrderHandler` до preflight записывает `ConfirmationAttemptStarted` (attemptId, immutable admissionId, owner, accepted total, startedAt) + durable `ConfirmationBarrierDeadline` due+310s. GET cancellation-status показывает blocker даже при operation=null. Пока нет `ConfirmationEffectsClaimed`, только winning fresh CAS может закрыть attempt как NotDispatched; старый worker обязан сначала выиграть EffectsClaim и потому не сможет вызвать wallet после закрытия. Read-only preflight failure не доказывает supplier refusal, но этот attempt ещё не имел side effects; response сохраняет safe reason. При supplier state inconsistency owner видит manual reason, не выдуманный paid/cancelled status.

Перед первым wallet call (Authorize) сохраняется `ConfirmationEffectsClaimed` с dispatchOwnerInstanceId и временем. Один winning worker выполняет существующую цепочку authorize→capture→supplier confirmation без повторного входа после EffectsClaim. Во всех redelivery/restart/retry API ветках claimed attempt только читается/передаётся в manual; не вызываются повторно Authorize/Capture/Confirm/Refund. Известный PaymentRef сохраняется событием `ConfirmationPaymentReferenceRecorded` после успешного authorize **до** capture; failure этой записи останавливает chain и оставляет unknown, без компенсации. Успешный Capture также записывается в `ConfirmationCaptureObserved` до вызова supplier confirmation; это receipt наблюдённого результата существующего test wallet, не банковская выплата. Failure этой записи прекращает chain и оставляет unknown. Late original worker после каждого awaited шага заново проверяет состояние attempt перед следующей side effect; это локальная защита, не внешний fence.

Успех добавляет existing PaymentAuthorized/OrderConfirmed и `ConfirmationAttemptCompleted` с проверенными minimal supplier payment facts в одном outbox commit. Для этого Core DTO `ConfirmedOrder` получает optional `SupplierPaymentEvidence` (reference, accepted Money, kind=Balance); Duffel mapper заполняет её только из уже проверенного succeeded receipt. Новому M3 writer отсутствие такой evidence после capture даёт unknown. Исторические OrderConfirmed events не переписываются. Эта evidence пригодна для D2 original-form classification новых заказов; старым историям не приписывается.

Любой error/save conflict/process interruption после EffectsClaim оставляет Unknown/ManualReviewRequired. Deadline: unclaimed admission закрывается CAS как NotDispatched; claimed незавершённый attempt становится ManualReviewRequired, money calls не делает. Late matching complete evidence может завершить attempt, прочие late replies не снимают barrier. Опубликованные deadline messages имеют immutable attempt/admission identity и current-version CAS.

Manual ConfirmBooking требует оба источника (wallet+supplier), ConfirmNoEffect — подтверждения отсутствия эффектов обоих участников и E4. Текущий DuffelTestWalletPaymentGateway хранит refs в памяти и не предоставляет durable ledger: после restart отсутствие его записи **не принимается** как отрицательное доказательство. Если нужных фактов нет, confirmation barrier остаётся manual; не вводится новый ledger, повтор capture, refund или автоматическая payment recovery. Такой исход и доступный operator review показываются пользователю, а не скрываются.

### E3. Внешние контракты, fresh reads и ограничения

Все новые owner mutations: JWT `flights:book`, GUID owner before state/body disclosure, no-store, 16KiB body limit, strict JSON/enum validation. New cancellation routes не входят в старый EF idempotency cache. В stream сохраняются prepare/consent request fingerprints (method/path/raw bytes SHA256) и stable request IDs; exact stage retry возвращает ту же operation с **актуальным** snapshot, а не frozen cached202. Разный payload/owner/stage не создаёт новую mutation. Истечение24h middleware cache не имеет отношения к этим claims.

| Route | Required body / response |
| --- | --- |
| GET `/api/flights/orders/{aggregateId}/cancellation` | Authoritative `CancellationStatusResponse`: aggregateId, bookingStatus, bookingVersion, operation nullable, blockingConfirmation nullable, serverNow. No supplier calls. |
| POST `/api/flights/cancellations/prepare` | aggregateId, operationId UUID, expectedBookingVersion. CAS owner/eligibility/current gate;202 current operation. Explicit new operation после завершённой предыдущей, не automatic replacement. |
| POST `/api/flights/cancellations/consent` | aggregateId, operationId, expectedOperationRevision, termsRevision, termsHash, noticeVersion=`cancellation-v1`, accepted=true.202 admission или409 stale/conflict. Hash/revision/notice server-checked. |
| POST `/api/flights/cancellations/abandon` | aggregateId, operationId, expectedOperationRevision.200 closed snapshot для известной завершённой unaccepted TermsReady/UnsupportedTerms, без active create sender/claim uncertainty; остальные409. UnsupportedTerms не закрывается по отсутствию terms: нужен сохранённый положительный факт завершения create без confirmation. |
| POST `/api/flights/cancellations/refresh` | aggregateId, operationId, expectedOperationRevision, refreshRequestId UUID.202 read work; no supplier mutation. Completed terminal result —200 без supplier call. |
| POST `/api/flights/cancellations/review/refresh` | Отдельный operator-only scope flights:cancellation-review; body aggregateId/operationId/expectedOperationRevision/refreshRequestId, только существующая Cancellation target. Тот же общий booking limiter и outcome predicates, без owner bypass обычного endpoint. |
| POST `/api/flights/cancellations/review/resolve` | Operator contract E1.200 current resolution snapshot;409 stale/inconsistent evidence,403 missing scope,404 absent target. |

`operation` содержит operationId/revision/phase/unknownStage, terms nullable, outcome, resolutionSource, reasonCode, dispatch state, nextRefreshAt, confirmedBookingVersion nullable. `blockingConfirmation` — discriminated union: kind=ConfirmationAttempt содержит существующие attemptId/revision/phase/reasonCode/canCloseNotDispatched; kind=LegacyHeld содержит targetId=aggregateId, revision=current bookingVersion и reasonCode=LegacyConfirmationUnverified, без выдуманных attemptId/attempt events; **не** ключи, payment secrets или пассажиров. Owner result не раскрывает внутренние process IDs и operator evidence refs. Terms view содержит local revision/hash, refund amount/currency/destination, expiry, whole-order route/count, notice и обязательный financialSource=SupplierApi|OperatorVerified; financialSource показывает происхождение финансовых условий независимо от operation.resolutionSource и отображается до consent и после success; supplier IDs остаются в серверном evidence, не browser URL/storage. Existing aggregate GUID — только order locator.

TermsHash использует fixed-field canonical encoding (формат1, booking+owner+operation, supplier order/cancellation binding, immutable route/party snapshot fingerprint, amount decimal invariant string, uppercase currency, normalized destination/composition, UTC expiry, terms revision, notice version). Hash вычисляет сервер; клиент возвращает его без пересчёта. Null amount/currency/expiry не превращаются в допустимые terms. Money.Create уже допускает zero и не допускает negative — отдельный денежный тип/FX не нужен.

Owner refresh разрешён не чаще **1 раза в60 секунд на owner+booking**, максимум одно принятое on-demand read одновременно. Admission через stream CAS сохраняет refreshRequestId/NextOwnerRefreshAt и durable Observe message. При конфликте identity/revision —409, при раннем новом запросе —429 + Retry-After (ceil remaining seconds) и current nextRefreshAt; duplicate последнего accepted refreshRequestId с тем же body возвращает текущее состояние без нового message. Новый owner/session не сбрасывает серверное ограничение. On-demand read имеет тот же общий10s budget и общий read-window с automatic reader; занятый window возвращает уже идущую проверку без второго GET. Он не создаёт новый recoveryEpoch и не расходует/сбрасывает четыре automatic slots.

Operator read-query вызывает только локальный stream. Resolve со ссылкой на сохранённую API observation не требует новой сети; явный operator refresh `/api/flights/cancellations/review/refresh` проходит тот же per-booking60s admission, не имеет unlimited bypass. Budget owner+booking берётся из authoritative booking owner, а не operator subject. Для Confirmation/LegacyHeld operator query остаётся локальным; support/payment facts получают по E4, новая автоматическая payment-read/recovery capability не добавляется. Owner GET polling: максимум один outstanding request на страницу, первые30s раз в2s, затем раз в10s пока вкладка видима; hidden/logout прекращает polling, manual/terminal — только явное refresh. GET никогда не запускает supplier calls и не очищает barrier.

### E4. Конкретный negative-unblock protocol и граница доказательства

Dispatch claim сохраняет process-lifetime `dispatchOwnerInstanceId` (случайный GUID на startup, не PID/hostname и не credential). Для первого среза manual post-dispatch negative outcome допускается только после operator quiescence procedure:

1. Закрыть mutation ingress для затронутого booking (его persisted barrier уже закрыт), остановить **все старые mutation-capable instances**, включая recorded dispatch owner, и отключить их outbound access. Зафиксировать в защищённой operation/support записи affected instance IDs, остановку process/container и блокировку egress; sleeping старый sender не считается остановленным по истёкшей lease.
2. Убедиться, что старые instances не возобновятся из suspended state. Replacement instance имеет новый ID; old queued Execute messages остаются fenced прежним claim/admission, не получают новое право на POST.
3. Получить **после остановки/egress isolation** положительное supplier/support подтверждение: этот exact cancellation/payment не исполнен и в supplier processing больше нет pending запроса, способного завершиться позже. Для confirmation нужны также wallet facts. Один GET null/404, absence in in-memory wallet, elapsed timeout или сам факт остановки процесса недостаточны: request мог попасть к поставщику раньше.
4. Privileged resolve прикладывает `quiescenceRef`, stoppedInstanceId (совпадает с persisted owner), stoppedAt, evidenceRef/category/observedAt и explicit final-no-effect attestation. Сервер проверяет binding, временной порядок и требования E1, затем одним current-revision CAS сохраняет OperatorVerifiedRejected и закрывает target. Unknown history остаётся. Если какой-либо пункт не доказан —409 insufficient evidence или RecordInconclusive, barrier сохранён.

LegacyHeld без marker не имеет recorded attempt/dispatch owner. Для этого target применяется отдельный typed `LegacyWriterDrain` attestation: targetId=aggregateId, current stream revision, drain всего поколения старых Flights writers и их egress, затем supplier+wallet positive no-payment/no-pending facts. Equality отсутствующему instance ID не требуется и не подделывается. CAS допускает только всё ещё owned Held/unmarked stream без новых attempts; при изменении state/version resolver возвращает409. Успешный review добавляет CoordinationEnabled+audit, не owner backfill и не confirmation/cancellation. При отсутствии фактов остаётся LegacyConfirmationUnverified.

Это предусмотренная ручная operational процедура, **не новый distributed fencing сервис и не утверждение, что приложение само проверяет состояние внешнего оркестратора или честность оператора**. Инфраструктурная справка доверена уполномоченному оператору; automated tests проверяют exact binding/required facts и stale-sender races управляемой моделью. Реальное выполнение остановки/egress/provision/deploy в эту задачу не входит. Для admitted-but-not-claimed попытки достаточно CAS закрытия E1/E2: старый worker не может выиграть subsequent EffectsClaim, поэтому внешний quiescence protocol не нужен.

### E5. Совместимость и поверхности доставки

Additive new event records и reader cases, без изменения V1/V2/V3 JSON identity и без source migration: состояния operation/barrier/refresh limiter живут в booking stream, scheduled messages — в существующем Wolverine store. Register каждого нового event в BookingAggregateConfig; OrderReadModelEventApplier обязан продвигать checkpoint на metadata events без изменения старых displayed fields. Rebuild/validate и event-replay fixtures включают новые facts. Existing notification versions считаются после всего batch, включая terminal operation event, не по прежним +1/+2 constants.

Startup не разрешает schema apply; rollout выполняется отдельно, после совместимых readers и остановки old writers. New Held coordination marker добавляется только новыми writers; old Held получает named manual gate без автоматической записи/перешифровки. Source docs/ADR0015/0016/0017/0023/current-state обновляются вместе с final product implementation, с ссылкой на этот единственный corpus; никаких параллельных новых specs/plans в Superpowers.

### E6. Completion критерия планирования

Plan tasks задают exact paths/interfaces/dependencies, local-vs-CI команды, named fault cases, exit criteria и независимый review. Все неопределённые operational случаи выше имеют явный Unknown/Manual terminal-for-automation путь. Недоступность доказательства — продуктовый результат, а не незавершённое проектирование. Code implementation, runtime CLI proof, DB CI и delivery имеют обычные execution gates и не выдаются за результаты текущего документального этапа.




Event/transport consistency: manual decisions всех трёх targets записывают `BookingOperationReviewRecorded` (target kind/id, resolutionId, validated actor, server time, payload hash, typed evidence/provenance) и отдельные outcome/coordination events в одной транзакции. Audit сам не меняет BookingStatus. `ConfirmationAttemptCompleted` сохраняет supplier evidence и ResolutionSource; `ConfirmationCaptureObserved` сохраняет только exact known test-wallet result до следующего external шага. Owner `GetCancellationStatusQuery/Handler → CancellationStatusResult` и privileged `GetCancellationReviewQuery/Handler → CancellationReviewResult` раздельны; оба не конкурируют за один Wolverine message. Role context никогда не берётся из request body.

## Дополнительное саморевью: повторы и завершённая подготовка

**S1 — порядок проверок и история identity.** Для prepare/consent/refresh/manual resolution порядок обязателен: authentication/scope → authoritative owner/target binding → lookup того же stable operation/request/resolution ID и проверка fingerprint → только для нового действия expected revision/current phase/expiry/evidence guards → CAS/write. Exact accepted retry проверяется **до** fresh revision/expiry guards: после успешного consent/review его исходный expectedRevision уже устарел, но это не новый запрос. Match возвращает authoritative результат той же принятой операции без повторных events/messages/notifications/provider calls; different fingerprint с тем же ID —409. Unknown прошлой операции не снимается replay позднего отказа.

Aggregate replay хранит currentCancellationOperationId и dictionary всех начатых cancellation operations/prepare+consent fingerprints в этом booking stream, а также resolution receipts по resolutionId. Закрытая операция не исчезает при новом prepare. Stable ID никогда не становится снова свободным после abandonment/expiry/restart. Нет TTL нового business dedup по аналогии с24h HTTP response cache; физическая история/retention вне текущей задачи. Owner/target authorization действует и на historical receipt.

Command response C4 добавляет `requestedOperationId` nullable, `currentOperationId` nullable и `isCurrentOperation`. Exact old replay возвращает requested historical operation snapshot плюс актуальный bookingVersion/currentOperationId, не подменяет его новой active operation. Owner GET возвращает current operation; requestedOperationId=null. Для текущего view isCurrentOperation=true (включая operation=null), для command replay это сравнение requestedOperationId с currentOperationId. Закрытая последняя operation остаётся current до следующего explicit prepare; отсутствие новой active mutation не удаляет её identity. UI/decoder не делают historical replay текущей карточкой при isCurrentOperation=false; выполняют ordinary status GET. Старый confirm success/cache response также не отменяет более новую cancellation evidence. Dict keys/receipts восстанавливаются чистым replay; DTO не раскрывает весь operation dictionary.

**S2 — UnsupportedTerms и refresh до claim.** Валидный pending quote response с достоверными exact order/quote IDs, положительным фактом завершения create и отсутствием Travel consent, но неподдерживаемым settlement/явно nullable financial terms, записывается как `CancellationTermsWereUnavailable` с validated creation-completion evidence. Это состояние UnsupportedTerms, не финансовая неизвестность уже отправленной отмены. Пользователь может закрыть такой review через abandon: CAS проверяет отсутствие consent/confirm claim, positive preparation completion и отсутствие pending create sender. Lost/malformed create response, active sender, unknown completion, Accepted или любой possible confirm остаются недопустимыми для abandon. Missing terms само по себе никогда не снимает barrier.

Refresh имеет явную матрицу: Succeeded/Rejected/Abandoned/Expired →200 local snapshot; Preparing или Accepted без dispatch claim →202 existing work, без нового Observe и без расхода provider-refresh budget; TermsReady/UnsupportedTerms с завершённой подготовкой →200 local snapshot (новые условия получают только новым explicit prepare после safe close). DispatchClaimed/Unknown/ManualReviewRequired с сохранённым recoveryEpoch →обычный60s read admission. Manual admission без epoch →200 local manual status/operator path, без Guid.Empty epoch или нового provider call. Operator refresh использует ту же матрицу; отдельный ручной resolver не подменяется refresh.

Audit receipt dedup выполняется до stale-revision guard, а `CloseNotDispatched` всё ещё требует отсутствия target side-effect claim. Event ordering нового hold: OfferHeldV3 **перед** BookingMutationCoordinationEnabled в том же commit; owner/held snapshot существует до marker replay. Notification version использует размер всего batch.


T4 refinement after independent review: observation starts persist ReadAllowed; false is a consumed/coalesced reservation with no supplier GET. Every dispatched read has retained operation+epoch+stage+start binding and immutable result identity. Prior-stage inconclusive replies may add history without changing current outcome. Refresh retains one accepted pending request across cooldown; an envelope coalesced with a busy read is consumed atomically. Overall uncertainty history remains separate from stage-specific refusal guards. Consent-bound financial provenance and actual observation origin are recorded separately; equal economic/proof predicates may cross SupplierApi/OperatorVerified origins only when both are valid.

C4 transport refinement: CancellationTermsView.RefundAmount is an invariant plain decimal string (no exponent or rounding), RefundCurrency is the supplier ISO code. This keeps exact supplier monetary consent across TypeScript without changing old price DTOs. Owner result excludes supplier/process/operator/payment references. ConfirmedBookingVersion reflects the authoritative loaded booking version plus actual committed event batch size for a terminal response; new GET uses its loaded version as the readiness floor.

### Execution refinements from independent review

Owner `operation.readPending` is a boolean derived from an accepted unconsumed refresh request or an active unexpired read window. Refresh returns202 for real pending read work even in ManualReviewRequired; terminal/local-only snapshots return200. It exposes no supplier IDs or audit refs. Operator review target selects the current nonterminal confirmation barrier before retained terminal cancellation history; a completed confirmation cannot hide the current cancellation target. Query includes typed scope/accepted amount/currency metadata required for manual binding, never passenger snapshots or raw supplier responses.

A supplier order cancellation fact is stored separately from consent-bound financial evidence, including facts discovered on initial read-only preflight. Eligibility/quote/effect/observation carry optional normalized OrderCancellation; the existing manual-review event can persist it without inventing an own success, provider return receipt or customer payout. Confirmed external order status is retained while unmatched own operation remains manual. Legacy Duffel bodyless cancellation stays unsupported before HTTP.
