# Design

## Context

See [proposal](proposal.md) and the base-bound [audit](research.md). Existing SSE transport, readiness and outbox work. The missing pieces are its browser consumer, notification coverage for retained report/refund changes, and read versions on order/creation. Current cancellation/refund contracts stay authoritative.

## Goals / Non-Goals

**Goal:** an owner keeps the order page open; a fictional webhook or committed refund/report result changes retained state; UI automatically reads and displays confirmed facts without repeating a command.

**Boundary:** read observation only. No Core state/event changes, migrations, new dependencies, supplier calls, consent/operation creation, resend, fare summary, real PSP, global notifications platform, auth/CI policy changes or live acceptance. Draft plan; implementation requires a new authorization.

## Decisions

### D1. Reuse server transport, add one invalidation kind

Keep `/events/flights/orders/{orderId}`, owner lookup, 15s heartbeat, channel/buffer limits and version coordination unchanged. Existing `OrderConfirmed`, `OrderTicketed`, `OrderCancelled` continue their readiness/current-status suppression and email behavior.

Add Application record `OrderChangedNotification(Guid AggregateId, Guid UserId, long RequiredStreamVersion)` in `Contracts/OrderNotifications.cs` and an overload in `Handlers/Notifications/PublishOrderSseHandler.cs`. Require existing `IBookingNotificationReadiness.RequireAsync`; publish `SseEvent("OrderChanged", aggregateId, empty JSON object, time.GetUtcNow(), order.ProjectedStreamVersion)`. Do not suppress this invalidation based on booking status: Cancelled can gain a new refund receipt/report. The body contains no money, PII, payment/provider/case/operation references. Use current EF checkpoint, never timestamp as sequence.

Enroll one notification alongside the existing reconcile/work in each **nonempty, materialization-eligible** batch at:

- `Cancellation/CancellationDecisionWriter.Persist`: cancellation phases, confirmation work and report review; retain legacy notifications and refund assessment unchanged.
- `Refunds/CustomerRefundWriter.Persist`: all six supported refund event kinds.
- `Handlers/Webhooks/DuffelWebhookHandler.HandleAirlineInitiatedCancellation`: report append; ticket path remains unchanged.

Materialization eligibility comes from retained source evidence, not an EF lookup: the loaded aggregate is Held/Confirmed/Ticketed/Cancelled/Refunded (already held), or the batch contains its first OfferHeld/OfferHeldV2/OfferHeldV3 event. Pre-hold creation review such as ConfirmNoCreatedOrder/RecordInconclusive through CancellationDecisionWriter must not enqueue this notification: its EF row intentionally does not exist and readiness would otherwise retry to DLQ forever. Such source-only outcomes use source GET fallback. A real delayed projection after Hold remains eligible and retryable. Keep existing work and legacy notifications intact regardless of generic eligibility.

Capture required version as loaded stream version + event count **before** AppendOne, exactly as existing writer convention. No-op/rejected/conflicting/rolled-back batch delivers none. Do not call registry directly from writers. Add the new type to `Api/Composition/BookingConsistencyHandlerPolicy` notification classification so existing retry/DLQ rules apply. Infrastructure implementations remain unchanged unless a focused test reveals an actual defect.

Same-version legacy/generic messages may coalesce in the registry. Thus every recognized client event refreshes all four read surfaces. No client logic can require receipt of a particular name at that version. Intermediate phases may coalesce to latest confirmed state; SSE is not an audit log.

Creation-only mutations keep current workflow polling plus fallback; this slice does not add broad notifications to every booking writer. Terminal creation/report views remain subscribed to later events.

### D2. Authenticated bounded streaming client

Create `shared/ts/api-client/src/flights-order-events.ts` with an order-specific fetch function and incremental parser; export from the existing package entrypoint. No new package. URL is same-origin, fixed path plus validated nonzero booking UUID; no query/hash. `GET`, `Accept: text/event-stream`, `Authorization: Bearer ...`, `cache: no-store`, `credentials: omit`, `redirect: error`, AbortSignal. Production requires token; only existing build-time fictional mode may omit it. Token and response body never enter logging/storage.

Recognize OrderConfirmed/OrderTicketed/OrderCancelled/OrderChanged. Decode only orderId, type and positive safe-integer streamVersion for invalidation; matching event/data type and current booking required. Ignore legacy payload/status for state; ignore unknown event kinds. Incremental UTF-8 decoder handles BOM, LF/CRLF/bare CR (including split delimiter), comments, multiline data, multiple frames/chunk and partial chunks. Unknown fields, id and retry do not create replay state or override bounded retry policy. Dispatch only a completed blank-line frame, discard incomplete EOF. Bound frame/partial-buffer to 64KiB; malformed recognized frame, invalid version, wrong booking or overflow closes connection and enters safe GET fallback with a generic error code (no raw data log).

Open means a 200 response with `text/event-stream` content type (parameters allowed) and readable body; first `: connected`/heartbeat updates liveness without triggering a business refresh. Fetch resolves after the endpoint's initial flush, hence registration precedes the mandatory post-open GET. Idle watchdog 45s; connect deadline 15s. Abort cancels reader/transport and clears timers/listeners.

### D3. One page lifecycle and explicit reconnect policy

New page-scoped `FlightOrderLiveUpdatesService` owns exactly one connection and refresh scheduler for `(bookingId, ownerId, identityEpoch, page generation)`. `start` is idempotent for the same normalized booking/owner/identityEpoch/page-generation key; it stops the previous generation only when that key changes. The auth service writes a new authenticated status object on every successful accessToken call, so object identity or an unchanged authenticated emission must not restart the page session. A changed token rotates only the connection generation. `stop` aborts stream, cancels timers/queued reads and invalidates callbacks. Checks run before and after every awaited token/fetch/GET and before applying results.

Start after authenticated page activation; initial GET works independently of SSE. After each successful SSE open, schedule a full GET cycle, even without an event. This covers the GET-to-subscribe gap and reconnect with no replay. Event version becomes a pending lower bound; duplicated/older hints never lower it or reset a recovery deadline. Connection-local version reset on reconnect is harmless because accepted GET watermarks survive within the page generation.

On network/EOF/wrong MIME/5xx/overflow use reconnect delays 1, 2, 5, 10, 30s capped at 30s; reset backoff only after 30s of healthy connection. Fallback reads continue at most once per 30s while visible, online and authenticated, **even when SSE appears healthy**, because missed events can be silent. Schedule one immediate GET after disconnect, then the periodic budget; avoid repeated immediate cycles during a reconnect storm. Honor a valid Retry-After for 429 up to 5min; periodic reads remain independent. A 204 disables SSE until explicit manual retry/page reopen and keeps GET fallback. A non-auth 4xx uses 30s retry, except 404 below. No global polling platform.

On SSE/GET 401/403 or accessToken failure, stop observation and revoke sensitive page/service state through the existing auth-failure path; require existing login flow. Do not loop token refresh after a denial. Call existing accessToken for each reconnect and 30s fallback cycle; if returned token differs, rotate the connection under a new connection generation, without changing identityEpoch. No auth service changes or token parsing are necessary.

Hidden/offline: abort stream and pause all automatic observation, including the existing creation/cancellation/refund workflow GET timers and their visibility callbacks; return to visible/online starts one coalesced applicable GET cycle and, when applicable, one new subscription. One page coordinator owns visibility/online triggers. Retained services route their old timers/callbacks through the same pause and single-flight gate instead of issuing an independent read. Use a read-only epoch/request counter to cancel or supersede GET completions during pause/deadline expiry; do not increment the mutation admission generation, clear known outcomes/consent or cancel an already admitted command solely to pause observation. Local terms-expiry bookkeeping remains active or is recomputed on resume; original deadlines and uncertainty barriers cannot be extended. A stale read/stream callback after hide/logout/owner change/navigation/destroy cannot mutate retained state. A still-current admitted command completion during observation-only pause continues through its existing mutation/owner guards. Business polling deadlines remain absolute; reconnect does not reset the 30s/190s workflow windows or server deadlines.

SSE 404 can mean EF ownership row is not ready, not permission to reveal state. If authoritative source GET establishes a Held-or-later booking but EF is still missing, keep source panels and bounded GET catch-up; defer the first SSE connection until owned order GET proves materialization. If an already established order stream later returns404, retry under the bounded policy. A source-only OfferQuoted resource is handled by the applicability matrix and does not repeatedly attempt SSE. For a direct resource where all owner reads return 404 and no retained same-owner evidence exists, stop automatic reads/subscription and show unavailable/manual refresh, preserving existing B3 behavior.

### D4. Versioned authoritative readers

Expose additive nullable `projectedStreamVersion` in `OrderResponse` from existing `OrderView.ProjectedStreamVersion`: map historical nonpositive EF sentinel (including the actual default -1) to null, never pass -1 through to the wire; update shared mapper consumers, TS types/decoder, fixtures and HTTP/OpenAPI snapshots. No database column. Positive safe integers on current responses; legacy missing/null/zero decodes as unknown-version compatibility, never as fresh proof and never replaces an already versioned snapshot. Reject negative/fractional/unsafe values.

Add `bookingVersion` to `BookingCreationStatusResult` and `BookingCreationResponse`. Read aggregate plus version from one Marten stream snapshot, following the existing owner status pattern (`[NonTransactional]`, IDocumentSession.Events.FetchForWriting, **no append/save/outbox**); do not AggregateStream then separately read current version, which can label stale fields with a newer checkpoint. Keep owner guards before returning anything. Extend TS creation decoder and consumers. Read-time diagnostic after 180s remains possible at equal bookingVersion when observedAt is newer; it may only preserve or reduce action permission. Lower-version response cannot reverse it. A later genuinely higher-version resolution can change the diagnosis.

Order, creation, cancellation and refund each retain their own accepted version. Do not compare caseRevision or operation revision to streamVersion. Cancellation/refund keep their additional existing revision/terminal guards and exact money strings. For any pending hint V, a response below V can populate an otherwise empty initial view as explicitly updating, but cannot declare synchronization; it cannot replace a newer snapshot or enable actions. Accepted stream-derived facts remain visible even when EF order GET is missing/behind. No timestamp or status ranking substitutes for version; existing status overlays remain as compatibility/command evidence.

The page target is the maximum of valid signal versions and accepted versioned GET snapshots, scoped to the booking and page identity. A read advancing this target queues one follow-up for older prerequisite panels, under the same catch-up budget; unknown legacy versions cannot satisfy a known target. Each action remains blocked while a newer hint or authoritative read proves one of that action's applicable prerequisite panels stale, using the matrix below; no blanket four-panel equality gate is introduced. Re-enable only from current authoritative read permissions and existing business guards, never from SSE. Do not restore checked consent after changed terms, phase, identity or reload. Reconciliation itself never calls prepare/consent/refresh-observation/confirm/refund/operator endpoints.

### D4a. Applicable readers and action prerequisites

Versions describe one booking stream, but not every resource exists at every stage. Determine applicability from a current owner-authorized creation snapshot, preserving any previously proven materialized order:

| Proven state | Read/stream applicability | Freshness/action treatment |
|---|---|---|
| No owned source snapshot and all owner reads404 | No known resource | Stop automatic observation; manual refresh/login path only. |
| OfferQuoted, never materialized; creation NotStarted/NotCreated/InProgress/ManualReviewRequired | Creation/cancellation/refund source reads apply; order EF and SSE are not yet applicable | Order404 is expected absence, not lag. It cannot block existing permitted fresh-quote/navigation action after proven NotCreated. InProgress/manual uncertainty still blocks writes according to current source guards. No invented order row or payout. |
| Held-or-later, or prior proven materialized order | All four reads apply; connect SSE once owned order GET succeeds | EF404/lower version is synchronization lag. Preserve source outcome and presentation. Catch-up budget then fallback; never downgrade applicability because a later stale response says OfferQuoted. |

Cancellation/refund status can validly return an empty/no-operation/no-case source snapshot; that successful versioned response satisfies freshness. A source404 after ownership was proven is a failed read, not an empty result. A source-only booking becoming Held switches order/SSE applicability on in the same generation. Activating observation does not assume that order/SSE is already applicable: source-only pages initially run source reads and fallback, while stream creation waits for an owned order GET. If creation read fails before applicability is known, independently probe order once; a successful owned order proves materialization, while a lone404 with other read failures is inconclusive and follows bounded retry rather than unavailable classification.

Action prerequisites preserve the current UI rules: confirmation needs existing visible Held order evidence plus fresh creation permission, cancellation blockers and report/refund guards; cancellation preparation needs fresh creation/cancellation/refund guards and the existing operation guards; quote/navigation recovery after NotCreated depends on fresh source permission, not an EF row that has never existed. Existing unknown-write/consent guards always win. Lagging EF may keep order details marked updating, but must not disable a source-authorized action whose existing guard does not require that EF data. Do not wait for all four versions to equal before rendering independent source results.

### D5. Coalesced reads and recovery

The page owns a full read cycle for applicable creation, order, cancellation and refund reads, as defined by D4a. Each reader has one in-flight read and one coalesced follow-up bit/maximum requested version, shared by manual, workflow polling, SSE and fallback triggers. Separate reads settle independently: failed creation must not prevent order/refund/cancellation refresh; failed order must not hide source state. Do not use fail-fast Promise.all to discard successful panels.

Refactor existing order loading into independent guarded creation/order reads; expose read-only completion methods on existing cancellation/refund services and reuse their decoding/update guards. Preserve their explicit action APIs and workflow polling. Read completions settle on success, error, supersession and stop; stop cannot leave a pending cycle Promise unresolved. A successful equal-version response acknowledges current freshness and clears its previous read error even when the snapshot object is not replaced; keep strict existing business/revision guards. A stale/rejected response does not acknowledge a newer target. Root service state updates also check the read-only epoch, because cancelling only the page subscriber would still let a leaf service accept a late GET. Do not reopen those root services for each signal: open/close resets user review state.

A hint at or below already confirmed applicable reader checkpoints is a duplicate and requests no new immediate cycle. For an outstanding target, only its first invalidation or a strictly higher target sets the coalesced follow-up; repeats of the same pending hint do not requeue after each completion. When a new V first arrives during GET started before V, queue one follow-up even if the current GET succeeds. Newer hints raise pending target. After response, preserve max accepted versions. If any applicable required source panel is below the target or temporarily 404, or a materialized order projection is lagging, retry at 2s within a 30s catch-up window started by the first outstanding hint; duplicates/new hints do not extend that window. Respect existing 15s HTTP timeout; at deadline cancel/supersede unfinished catch-up reads and invalidate callbacks. After budget exhaustion preserve last good snapshots, display synchronization pending and return to 30s fallback/manual GET. A successful later read resumes normal rendering. Once the catch-up budget expires with a target still outstanding, subsequent repeated hints keep slower fallback and cannot reopen the2s loop. Within an active lifecycle a new automatic catch-up window is possible only after the previous applicable target has converged and a later change raises it. Resume after hidden/offline begins a new observation epoch and clears the old catch-up budget before its required fresh GET; page reopen creates a new session. Neither boundary extends business deadlines. No busy spin on repeated bad data.

Implementation rulings from source review: command freshness is checked at actual cancellation leaf admission, including direct child-component calls; admitted commands retain their existing owner/business/expiry guards during observation pause. Equal-version reads for the same operation and terms key keep the minimum known local expiry; a new operation/terms key resets consent. Each connect/resume/disconnect freshness epoch requires a read begun after that boundary, independently of the retained snapshot version. Token acquisition is bounded by the observation deadline without changing the auth SDK; its timeout is a read/transport failure, not authorization denial. The new safe notification is included in the existing diagnostics/replay allowlist, while dispatch types remain excluded.

A full cycle is single-flight with one queued cycle; signals within it coalesce. Existing workflow timers must route through the same per-resource gate; they may request reads within their original 30s/190s windows but cannot create parallel same-resource requests. Manual refresh reads all four surfaces (current page refresh omits refund). UI shows a quiet message after failure: «Не удалось обновить данные. Показан последний полученный результат.» Connection recovery is separate from business uncertainty; a connected stream alone never clears a read error. Live refresh does not move keyboard focus or repeatedly announce unchanged content.

### D6. Fictional demonstration and evidence

Add a dedicated startup preset to the existing Node demo. A retained fictional order changes on one shared deterministic server-side schedule started once after its first stream registration, independently of GET count; reconnects and additional subscribers never restart or advance that schedule: ticket webhook first, a separate report preset for unverified airline cancellation, refund preset for a later fictional receipt. No runtime API to reset barriers or mark a real order paid. SSE uses the same event wire shape and incremental flush; demo remains loopback-only, refuses Authorization, accepts only fictional identities and is unreachable in production builds.

Node/browser tests assert state before and after the scheduled webhook, a real open stream and subsequent GET, dropped/duplicated hints, reconnect, failed GET, long-idle terminal order, auth/navigation cleanup and **zero mutation requests caused by observation**. Demo cannot prove HMAC, JWT, persistence or outbox. Existing CI owns signed fictional webhook -> inbox/outbox -> stream -> EF readiness -> SSE -> owner GET proof. Host/DB/Aspire tests run there only; PR E2E remains mandatory on dev/master with policy unchanged.

## Risks / Trade-offs

- One-process best-effort delivery and restart loss → mandatory reconnect GET plus 30s fallback; no bounded freshness claim while network/projection is unavailable.
- Extra four-GET cycle every 30s per visible order page → coalescing, hidden/offline pause, no list-page or cross-tab framework; review observed load before any expansion.
- New durable notification type → readers/handler must exist before emitters; retain consumer for rollback with messages pending.
- GET versions make additive shared DTO surface larger → audit list/cancel fixtures and generated OpenAPI as well as detail page.
- Four independently observed versions are not an atomic cross-resource snapshot → keep synchronization explicit and conservatively block actions while prerequisite panels lag; server guards remain decisive.
- Long-lived HTTP auth checks happen at connection setup → client rotates on refreshed token and tears down on auth changes; no claim of new immediate server-side token revocation.
- Equal-version creation timeout is derived from server observation time → test transition at180s without stream append; never use it as proof of failed supplier effects.

## Migration Plan

No EF/Marten schema or historical event migration. When separately authorized: ship additive GET fields and new notification handler before enabling new emitters/UI; old UI ignores fields and generic event. New UI accepts absent-version legacy responses conservatively and relies on existing evidence guards. Verify existing dev events proxy and separately approved deployment proxy streaming/buffering/timeouts.

Rollback the UI independently to existing manual/workflow reads. Disable new emitters before removing their handler; drain retained notification messages or keep compatible consumer. Do not downgrade to a binary unable to read the already merged refund/ancillary events. No rollout, drain or deployment is executed by this planning change.
