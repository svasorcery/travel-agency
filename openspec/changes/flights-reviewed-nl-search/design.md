## Goals / Non-Goals

Первая версия заполняет поля русскоязычной формы для одного направления или поездки туда-обратно. Запрос с явными детьми, составным маршрутом, особым классом или валютой получает пояснение об ограничении формы. Нельзя молча превратить такой запрос в перелёт для взрослых экономклассом в RUB. Составной маршрут по-прежнему доступен в ручном режиме. В объем входят поле с фразой, одна операция разбора и ручные уточнения в форме. Чат, история диалога, бронирование по тексту и агентная платформа выходят за эти границы.

## Decisions

### 1. У разбора собственная операция

Предлагаемый `POST /api/flights/search/nl/preview` принимает `{query, referenceDate}`. Страница передаёт локальную календарную дату из того же `localToday()`, которым валидирует форму, зафиксировав её при нажатии «Заполнить форму». Сервер проверяет ISO date-only и использует значение только для интерпретации текста. Время исполнения и сроки ожидания по-прежнему измеряются через `TimeProvider`. Заполнять форму можно анонимно, как при обычном поиске.

Успех, включая пустой или частичный разбор, — HTTP 200. Wire DTO preview содержит `tripType` (`oneWay` / `roundTrip` / `null`), `origin` и `destination` (`{code, name}` / `null`), `departureDate` и `returnDate` (`{value, source}` / `null`, ISO date-only, `source = explicit | suggested`), `passengerCount` (1–9 / `null`) и массив `issues` с полем и причиной (`missing | ambiguous | unsupported | invalid`). Для проблемы всего запроса используется поле `request`. Вопросы локализует UI. Для обычного перелёта в одну сторону отсутствие даты возврата допустимо. Для явно запрошенного обратного рейса это незаполненное обязательное поле. Дата проверки — обязательное поле запроса `referenceDate`. Неверный ввод даёт 400, превышение размера тела — 413, исчерпание лимита — 429. При выключенной функции — 404 до отправки в AI, при недоступности, тайм-ауте или нарушенной структуре ответа — 503 ProblemDetails. Успешные и ошибочные ответы preview используют `Cache-Control: no-store`.

Ниже приведён общий образец HTTP 200 для тестов Host и декодера Angular. Дата формы — 2026-11-23.

```json
{
  "tripType": "roundTrip",
  "origin": null,
  "destination": {"code": "AER", "name": "Сочи"},
  "departureDate": {"value": "2026-11-28", "source": "suggested"},
  "returnDate": {"value": "2026-11-29", "source": "suggested"},
  "passengerCount": 2,
  "issues": [{"field": "origin", "reason": "missing"}]
}
```

Flights Application запрашивает отдельное типизированное сообщение разбора и возвращает черновик. У этой ветки нет отправки `SearchFlightsQuery`, доступа к поставщикам, поиска из кеша или вызова старого NL endpoint. Для Core NATS добавить собственные идентификаторы запроса и ответа, subject и стабильную queue group по образцу [ADR 0020](../../../docs/adr/0020-nl-search-cross-service-contract.md). Это позволяет старому клиенту и новому UI одновременно работать с разными типами результата. Изменение семантики старого POST или его обязательных полей нарушило бы контракт v1.

### 2. Модель указывает текст, приложение проверяет значения

Модель возвращает короткие фрагменты исходного текста для роли города, дат, числа пассажиров и типа поездки. В поле `restrictions` она может указать фрагменты с неподдержанными условиями. Все ключи обязательны, пустой слот имеет значение `null`, пустой список ограничений — `[]`. Неверная структура целого ответа ведёт к ручному вводу. Ошибка отдельного фрагмента даёт 200 с вопросом у соответствующего поля и сохраняет остальные проверенные значения.

Flights сверяет фрагменты и их роли с исходным текстом целиком. Например, «в Сочи» подтверждает прибытие, «из Москвы» — вылет, «нас двое» — двух взрослых при отсутствии указания на детей. Проверки явных признаков первого среза учитывают оба варианта в «из Москвы или из Петербурга», отрицание «не из Москвы», «только туда», «туда-обратно» и указание на ребёнка, даже если ответчик пропустил уточняющий фрагмент. При противоречии система запрашивает выбор. Для явно неподдерживаемого состава пассажиров, класса, валюты или нескольких участков показывается ограничение и блокируется поиск по этому разбору. Пользователь может явно выбрать «Заполнить вручную», вернуться к своим ручным значениям и составить поддерживаемый запрос. Такая смена режима сама поиск не отправляет.

Использовать один локальный список названий, падежей и кодов, доступный нормализатору Flights и полю уточнения. Для первого среза достаточно Сочи → AER, Москва → MOW и Санкт-Петербург → LED, а также прямого ввода трёхбуквенного кода. Для Москвы сохраняется городской код. В поле с вопросом «Из какого города вылетаете?» человек может выбрать «Санкт-Петербург (LED)» по названию или ввести LED. В прежний контрол попадает канонический код. Неизвестное название оставляет подсказку о вводе кода; сетевой справочник аэропортов не нужен. Ручное изменение кода снимает прежнюю подпись города. Режим составного маршрута сохраняет правило явных кодов аэропортов.

При «на выходные» сервер выбирает ближайшую субботу, включая текущую, и следующее воскресенье. Воскресный запрос относится к следующим выходным. При явном «только туда» предлагается только вылет. Явная дата возвращения имеет источник `explicit` и приоритет над предложенным воскресеньем. Если запрошено «туда-обратно» для точной даты вылета, а день возврата отсутствует, форма открывает пустое обязательное поле возвращения. При одновременном указании несовместимых вариантов поле типа поездки или даты требует выбора. Метка «Предложено по фразе „на выходные“» относится только к вычисленным датам. После ручной правки соответствующая метка снимается.

Явный обратный рейс, дата возврата или предложение обоих дней выходных дают `roundTrip`. Явное «только туда» даёт `oneWay` и очищает дату возврата. Когда фраза не задаёт тип поездки, в preview он равен `null`. Форма оставляет выбранный вручную режим или использует своё начальное «В одну сторону». Если ручной режим противоречит новому предложению, конфликт разрешается в форме.

Пример содержимого вымышленных ответов `IChatClient` для трёх сценариев при дате формы 2026-11-23. Строки в успешных ответах — фрагменты исходного запроса до нормализации.

| Случай | Ответ тестового AI | Что проверяет клиент |
| --- | --- | --- |
| Полный | `{"origin":"Из Москвы","destination":"в Сочи","departure":"12 декабря 2026","return":"обратно 15 декабря 2026","party":"двое взрослых","tripType":null,"restrictions":[]}` | MOW, AER, две явные даты, два взрослых. Ручная замена 15-го на 16-е попадает в поисковый запрос. |
| Неполный | `{"origin":null,"destination":"в Сочи","departure":"на выходные","return":null,"party":"нас двое","tripType":null,"restrictions":[]}` | Вылет пуст, AER, две предложенные даты и два взрослых. Вопрос о вылете исчезает после выбора Санкт-Петербурга. |
| Недоступность | Тестовый ответчик завершает вызов по тайм-ауту. | Поля LED и 2, введённые до разбора, сохраняются; после ручного заполнения остальных полей поиск доступен. |

На новом пути действуют существующие [лимиты Flights NL](../../../docs/operations/2026-10-16-nl-search-limits.md). [AncillaryRequestBodyGuard](../../../modules/flights/Travel.Modules.Flights.Api/Middleware/AncillaryRequestBodyGuard.cs) сравнивает путь целиком. Добавить preview в эту проверку до привязки тела (16 КиБ, включая chunked) и подключить существующую HTTP-политику `flights-nl-search`. Обе операции используют общий лимит, 1000 символов и общий admission AI. Считать фактический размер нового промпта и схемы. Включить новый тип сообщения в политику завершения без повторов и использовать его собственный идентификатор в строке учёта. Host ограничивает ожидание шестью секундами, AI — пятью секундами на обработку, как на действующем пути.

Общий `IChatClient` в [Travel.AI](../../../apps/Travel.AI/Program.cs) уже связан с Anthropic. Для preview выбрать клиент по отдельному ключу. При бюджете $0 тестовая композиция регистрирует под этим ключом только вымышленный ответчик; вне неё без разрешённого обработчика preview недоступен. Отсутствие регистрации, флаг preview или имеющийся ключ v1 не должны приводить к выбору общего клиента. Обращение по новому subject подчиняется тому же ограничению. Текст и черновик живут в пределах запроса и страницы. С учётом глобальных durable local queues Host проверить также отсутствие тела в долговременных очередях и ошибках доставки. Строка учёта содержит только служебные поля.

### 3. В форме два явных действия

«Заполнить форму» — `type="button"`. Набор текста, Enter в поле фразы, получение ответа и правки не вызывают `submit()`. Один актуальный ответ обновляет контролы одним согласованным изменением и задействует обычный сброс устаревшей выдачи. Выбранная поездка туда-обратно сразу открывает поле возвращения. Вопрос привязан к соответствующему полю, статус и изменения доступны с клавиатуры и для скринридера.

В обычном ручном режиме форма по-прежнему стартует с одного взрослого. В режиме разбора различать исходные значения формы, ручной ввод и предложения текущей попытки. Успешный ответ заменяет предложения предыдущей фразы. Для отсутствующего обязательного поля оставить ранее введённое вручную значение или показать пустой контрол с вопросом. В частности, для пропущенного числа пассажиров на свежей форме показать «Сколько взрослых летит?» и возможность выбрать 1–9, включая одного. Начальная единица не закрывает вопрос. Если новое распознанное значение конфликтует с ручным, показать оба в этом же поле и дать выбрать, какое использовать. Явное возвращение к ручному заполнению сбрасывает вопросы разбора и сохраняет ручные правки.

Состояние уточнений участвует в проверке перед `submit()` и `retry()`. Синтаксически допустимого кода или числового значения недостаточно, пока по этому полю открыт конфликт. Вопрос виден сразу после разбора, даже когда существующий `fieldError()` ещё скрыт до первой отправки. Выбор города, числа или даты снимает соответствующий вопрос локально. Готовая форма отправляется действием «Найти рейсы» с мыши или клавиатуры.

Привязать ответ к номеру попытки и версии правок. Изменение текста, ручная правка во время ожидания (даже с возвратом к прежнему значению), смена режима, ручная отправка или уход со страницы делают старый ответ неприменимым. Двойная активация заполнения во время одной попытки отправляет один preview. Ввод фразы держать вне группы поисковых параметров, иначе её набор запустит подписку `form.valueChanges` и преждевременно сбросит выдачу и выбранное предложение. При ошибке сохранить текущие поля и ручной поиск. При успешном заполнении применить изменение к поисковым полям и использовать их обычный сброс устаревших результатов.

## Risks / Trade-offs

| Риск | Как проверить решение |
| --- | --- |
| Разбор или неявный submit всё-таки запускает поиск | Считать отдельно HTTP-запросы Angular, отправки команды поиска и вызовы тестового `IFlightSearchProvider`. Проверять нули до нажатия, в том числе для полного ответа и невалидного submit. Для валидного submit с одним подходящим тестовым поставщиком и пустым кешем ожидать один структурированный запрос и один вызов этого поставщика. |
| Старый ответ затирает новый выбор или город получает неверную роль | Задержать ответ до ручной правки. Для исходной фразы про Сочи подложить вымышленный MOW без подтверждения и отдельно попытку назначить «в Сочи» вылетом. Проверить поля и счётчики. |
| Успех фикстур создаёт ложное впечатление о качестве распознавания | В [сценариях приёмки](specs/flights-reviewed-nl-search/spec.md) заданы фразы, календарь, ожидаемые поля и действия. Тестовый `IChatClient` выдаёт подготовленные ответы либо ошибку. Работа с живой моделью требует отдельного бюджета и оценки. |

## Migration Plan

Изменение добавляет маршрут и сообщения рядом с v1. Флаг preview по умолчанию выключен. Для локальной приёмки обе стороны включают preview с вымышленным ответчиком. При отключении preview страница позволяет продолжить вручную, старый NL-маршрут использует собственную конфигурацию. Изменение не требует миграции БД.
