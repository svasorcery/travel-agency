# Дизайн смены жилья в Trips

## Context

Сценарий и границы описаны в [предложении](proposal.md). До изменения деталь плана, строгий клиент и канонический защищённый снимок использовали необязательный объект `manualStay`. `TripPlanService` проверяет владельца и точную ревизию, а `TripPlanStore` атомарно заменяет одну строку. Построение страницы сводок тоже читает снимки. Поэтому несовместимый снимок может сделать недоступной целую страницу списка на предыдущей версии Host. [Контракт рабочей области](../../../specs/trip-plan-workspace/spec.md) · [Предыдущий дизайн](../2026-11-24-trips-manual-stay-calendar/design.md)

## Goals / Non-Goals

Цель — хранить весь ручной список в одном плане и обеспечить предсказуемую работу старых вкладок и откат без потери записей. Границы среза охватывают агрегат Trips, его защищённый снимок, detail GET/PUT и редактор. Подтверждённый заказ Hotels отображается по [своему контракту](../../../specs/trip-hotel-reservation-links/spec.md). Flights, Hotels и дневные блоки сохраняют собственные источники, операции и правила календаря.

## Decisions

### 1. Один список в агрегате и одна операция сохранения

- `TripPlan` хранит коллекцию существующих значений `TripManualStay`, отсортированную по заезду. Даты остаются `DateOnly` пункта назначения. При восстановлении и замене проверяются название, обе границы диапазона, хотя бы одна ночь и пересечения итогового списка. Общая дата выезда и следующего заезда допустима. Для плана в 1–14 календарных дней естественный предел составляет 13 записей. Этот предел применяется при приёме массива до предметной проверки.
- При конфликте дат диапазона используется `409 Trips.DateRangeWouldExcludeStay`, при общей ночи `409 Trips.ManualStaysOverlap`. `ProblemDetails` передаёт код ошибки без содержимого плана. Смена города требует сначала отдельного сохранения пустого списка, даже если запрос смены города тоже прислал пустой список. Сохраняются действующие проверки блоков и диапазона.
- Новый набор хранится в том же снимке и меняется в той же операции `If-Match` и атомарной замены по владельцу и ревизии. Равные канонические значения, в том числе присланные в другом порядке, сохраняют ревизию и время. Отдельная таблица проживания потребовала бы согласования двух записей и увеличила бы объём изменения.
- Angular применяет форму к копии списка, заменяя выбранную запись перед проверкой пересечений. Ошибка оставляет ввод доступным, а в календаре виден последний применённый список. В день переезда ручные события показывают выезд, затем заезд. Даты ночей считаются до выезда исключительно. Обычное сохранение отправляет полный снимок черновика, включая прежний список при правке других полей. Действующие защиты от запоздалых ответов распространяются на список целиком. После позднего ответа отображаются более новые правки, а конфликт или неизвестный результат требует явного перечитывания.

### 2. Совместимые контракты для старой и новой вкладки

Новая вкладка читает и сохраняет через `GET` и `PUT /api/trips/{tripId}/workspace-v2`. Текущие `GET` и `PUT /api/trips/{tripId}` остаются контрактом v1. Отдельный адрес выбран вместо заголовка версии. Предыдущий Host не обслуживает новый адрес, поэтому даже запоздалый v2 PUT после отката не попадёт в старый обработчик замены. Обе версии используют существующую точную числовую ревизию и общую команду сохранения.

| Случай | GET и ответ успешного PUT | Вход PUT |
| --- | --- | --- |
| v1, в сохранённом плане 0 или 1 запись | Прежняя строгая деталь. Поле отсутствует для 0 записей, `manualStay` содержит объект для 1. | Пропуск поля сохраняет текущую запись, `null` удаляет её, объект заменяет. |
| v1, в сохранённом плане ≥2 записи | `409 Trips.PlanVersionRequired` вместо частичной детали. Старая вкладка использует действующий экран конфликта. | После проверки владельца и ревизии точный запрос получает тот же `409` при любом состоянии поля. Устаревший запрос получает `412`. |
| v2, любое допустимое число записей | 0 и 1 используют прежнее каноническое представление. При ≥2 есть только `manualStays` с полным списком. | Требуется `manualStays` с итоговым массивом, включая `[]` для явного удаления всех записей. `null`, `manualStay` и смешанные формы получают `400`. |

В v1 PUT проверка количества выполняется на **той же загруженной ревизии** внутри операции замены, до её записи. Такой порядок исключает гонку с v2 и успешный ответ, который старый клиент не может прочитать. Корректный запрос к чужому или отсутствующему плану получает прежний `404` без данных. POST создания, список и DELETE используют текущие адреса и контракты. Список сохраняет прежнюю форму даже со смешанными версиями снимков. Новое приложение читает ответ POST строгим v1-декодером, открывает существующий план через v2 и отправляет PUT только туда. После отката доступ к редактору возвращается при загрузке совместимой версии web. Устаревшая вкладка показывает существующую ошибку доступа к плану, удерживает локальные правки и пользуется обычным предупреждением при обновлении страницы. Новый клиент не повторяет PUT автоматически и не переносит его на адрес v1.

Деталь без дополнительных полей при 0–1 записи сохраняет возможность открыть ранее принятый план около лимита 128 КиБ. `ITripPlanCodec` разделяет строгое чтение форматов и измеряет полную каноническую деталь с действующим резервом. Проверку проходят ответ и снимок до записи, включая проверку временного плана с прогулочными блоками. Маршруты, обе формы ответа и коды отказа отражаются в OpenAPI.

### 3. Версия защищённого снимка в существующем контейнере

| Содержимое плана | Представление в `trips.trip_plans.protected_payload` |
| --- | --- |
| 0–1 ручная запись | Тот же Base64-конверт, канонический JSON v1 и прежняя криптографическая привязка. |
| ≥2 ручных записей | `v2:` и Base64-конверт. JSON содержит канонический `manualStays`. Защита привязана к версии `2`, владельцу, ID плана и ревизии с тем же набором ключей. |

`TripPlanBinding.SchemaVersion` уже входит в назначение защиты, а `TripPlanEntity` хранит только `protected_payload`. Infrastructure определяет версию по контейнеру, проверяет его размер до распаковки и передаёт проверенную версию каноническому декодеру. Неизвестный префикс, несоответствие версии и формы, подмена префикса и повреждённый контейнер дают `Trips.Unavailable`. Подмена проверяется криптографически. Предыдущий Base64-декодер отвергает двоеточие.

Версия выбирается по окончательному списку при каждой эффективной записи. Обычное явное сокращение списка до 0–1 переводит тот же план в v1 атомарно с новой ревизией. Чтение и no-op сохраняют байты и ревизию. Метка видна только в конверте хранения и указывает грубый класс формата. Имена, даты, количество записей и прочие поля остаются внутри шифротекста. Схема EF и хранилище ключей используются в существующем виде. ## Risks / Trade-offs

- Старая вкладка сможет редактировать планы с 0–1 записью. Для плана с несколькими записями ей потребуется обновление приложения. Отказ сохраняет все данные и точную ревизию вместо показа неполной детали.
- Смешанный пул старых и новых Host с общей БД небезопасен после первой записи v2. Поставка и обратное переключение требуют короткой остановки и завершения операций Trips на всех экземплярах.
- После первой записи v2 откат к Host, который читает только v1, зависит от данных. При необходимости быстрого восстановления с сохранением планов используется совместимый с v2 Host либо существующее отключение Trips до исправления.

## Migration Plan

Этот порядок относится к будущей отдельно согласованной поставке. Для проверки используются вымышленные данные, одноразовая БД и ключи. Предыдущая пара Host/web для локальной проверки берётся из подтверждённой базы `4bd31d844323652038f0264191c277aaaf5b2ae3`. В среде поставки фиксируется фактическая предыдущая совместимая пара.

1. До поставки проверить v1/v2 в одноразовом контуре с сохранёнными старыми планами и вымышленным снимком v2, который открывается после перезапуска. При переключении завершить операции Trips на всех экземплярах прежнего Host и убрать их из обслуживания Trips. Затем запустить новый Host и соответствующий web с той же схемой и ключами, подтвердить готовность и открыть приём запросов.
2. Перед возвратом Host с поддержкой только v1 снова остановить приём всех запросов Trips и дождаться окончания операций на всех экземплярах. На основной БД выполнить только агрегатную проверку через разрешённый read-only доступ. Двоеточие лежит вне алфавита Base64 и обнаруживает контейнер любой версии с меткой.

   ```sql
   SELECT COUNT(*)
   FROM trips.trip_plans
   WHERE strpos(protected_payload, ':') > 0;
   ```

3. При достоверном нуле и сохранении остановки вернуть проверенную пару Host/web. На тех же данных и ключах сверить готовность и чтение через v1 в рамках разрешённой проверки, затем открыть операции Trips. Обычное сохранение на предыдущей версии проверяется в одноразовом контуре. Уже открытая новая вкладка получит отказ от предыдущего Host на `workspace-v2` и сможет загрузить совместимый web при обновлении страницы.
4. Положительный счётчик либо невозможность его подтвердить блокируют возврат к Host с поддержкой только v1. Сохранить текущие данные и ключи, использовать проверенный Host с чтением v2 или запустить Host с `Trips:Enabled=false` до совместимого исправления. Повторное решение проходит ту же остановку и проверку. Процедура возврата использует текущие данные, контейнеры, ключи и схему.
