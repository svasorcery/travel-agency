# Rail M1: поиск через Yandex.Rasp в интерфейсе Travel

## Why

На исходном base Rail содержал только scaffold. Нужен полезный первый поиск поездов РФ в собственном интерфейсе: расписание и те сведения о билетах и цене, которые действительно отдаёт выбранный пользователем Yandex.Rasp, без бронирования и выдуманного наличия мест. Source implementation и независимые от него pending acceptance gates отражены в [verification.md](verification.md).

## What Changes

- Добавить выбор конкретных железнодорожных станций РФ, даты отправления и вида сообщения: поезда, электрички или оба вида. Первый срез ищет прямые поездки; пересадки и составные маршруты остаются следующими этапами.
- Подключить один официальный источник Yandex.Rasp через Rail Infrastructure. Fake и вымышленные HTTP fixtures проверяют тот же контракт и не считаются второй внешней интеграцией.
- Показать номер/название рейса, станции посадки и высадки из выбранного расписания, местные даты/время с предоставленным offset, длительность и доступные необязательные сведения источника. Проверять echo станций/даты даже в пустом ответе. Не считать `start_date` подтверждённой датой начала полного рейса. Это расписание, а не фактическое движение поезда.
- Включить в M1 отображение `tickets_info`, если оно возвращено: тип билета, точную поддержанную сумму/валюту и независимый признак возможности электронного билета. Повреждённая/неподдержанная цена не стирает другие валидные факты; неполнота билетных сведений явная. Не превращать `places` в количество мест или схему вагона; отсутствие цены не означает ноль, отсутствие сведений не означает sold out. Не обещать наличие или цену на весь состав пассажиров.
- Различать unsupported/skipped, complete-empty, complete, partial/limited и failure в API и UI. Ограничивать ожидание, число запросов, ответ, кэш, каталог станций и удерживаемую память; отменять устаревший поиск.
- Использовать только временные process-local данные, полноценную атрибуцию Яндекса (официальный баннер, уведомительный текст и ссылка) и собственные вымышленные fixtures. Кэшированный reference bundle объединяет каталог и безопасно нормализованную атрибуцию; ожидающие callers также ограничены. По истечении срока данные уходят из server и UI memory. Не создавать постоянный каталог, raw archive, историю поиска, БД, миграции, журнал билетов или новые общие frameworks.
- Оставить настоящий источник default-off. Самостоятельные проверки используют terminal fictional transport с запретом внешней сети. Доступ/ключ/квота/права, настоящие запросы, измеренный load/performance и target rollout требуют отдельных разрешений и receipts.

## Capabilities

### New Capabilities

- `rail-schedule-search`: поиск прямых железнодорожных поездок между станциями РФ, временный выбор станций, достоверное отображение расписания и необязательных билетных сведений, ограниченное выполнение и собственный UI.

### Modified Capabilities

Нет. Контракты Flights, Hotels и Support не меняются.

## Impact

- Будущая реализация: существующие четыре проекта `modules/rail`, пустые `tests/rail`, новая `Rail.Api.Composition` facade и её единственная точка подключения в Host. Внешние DTO, auth, протокол, streaming parser и mapping остаются в Infrastructure; Core и Application не импортируют HTTP/provider DTO или внутренности других модулей.
- Будущие API: `GET /api/rail/stations?q=...` и `POST /api/rail/search`. Angular `/rail` использует существующий UI kit и отдельный Rail consumer в `shared/ts/api-client`; строгие декодеры не принимают provider wire JSON как публичный контракт.
- Потребуются целевые обновления architecture inventory/positive selectors, Host OpenAPI, HTTP и fictional browser checks. Текущие запреты на scaffold wiring снимаются только для реализованного Rail milestone, а не для Trips и не путём ослабления общей политики.
- Новые пакеты, paid/AI integration, БД, event sourcing, broker, Redis, миграции и изменения security backport не требуются. Существующий набор зависимостей и braces proof сохраняется.
- Исследование выполнено на чистом `dev`, равном обновлённому `origin/dev`: `799e31a6b31ff256ba017861cd911e547e4e9896`. Это исходная точка исследования, а не разрешение откатить будущий dev или заменить явно запрошенную базу ветки текущим HEAD.
- Этот change содержит только проектирование. Его подготовка не означает принятия спецификации или начала реализации. После отдельного утверждения реализацию выполняет отдельный агент `gpt-6.1-sol`, затем основной агент лично проверяет результат.

Официальные источники, принятые решения, предложенные численные ограничения и оставшиеся внешние вопросы собраны в [design.md](design.md). Проверяемые требования: [specs/rail-schedule-search/spec.md](specs/rail-schedule-search/spec.md); выполнение: [tasks.md](tasks.md).
