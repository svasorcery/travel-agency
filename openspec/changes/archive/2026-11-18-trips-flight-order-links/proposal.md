# Proposal

Статус на 17 ноября 2026 года — предложение принято с пятью правками саморевью.

## Why

Путешественник уже может сохранить план поездки и оформить авиазаказ, но между ними нет проверяемой связи: маршрут приходится искать в другом разделе или переписывать в заметки. Следующий законченный шаг — прикрепить собственные авиазаказы к плану, видеть состояние, известное Flights, и переходить к управлению заказом из поездки.

## What Changes

- Добавить к сохранённой личной поездке отдельный раздел «Авиазаказы»: выбор своего существующего заказа, явное прикрепление, чтение и удаление связи. Согласованный предел первого этапа — четыре разных полных заказа на поездку; один заказ может содержать все свои 1–4 flight legs. Один заказ разрешено связать с несколькими поездками того же владельца.
- Сохранённая связь означает выбор пользователя, а не покупку, подтверждение пригодности маршрута или автоматическую укладку перелёта в календарь. Даты, город, число участников, блоки и денежные оценки плана автоматически не меняются. Отменённый заказ можно оставить как часть истории.
- В разделе показывать минимальные сведения о целом заказе: все его legs, аэропорты, сохранённые даты/время с исходными offsets, количество пассажиров, известное состояние/неопределённость и момент наблюдения. Статус описывает данные Travel Flights, не текущее движение самолёта или live-проверку поставщика. Ссылка ведёт на существующую страницу авиазаказа.
- Trips проверяет владельца заказа через новый узкий опубликованный контракт Flights. Привязка проверяется по authoritative booking stream; выдача списка кандидатов остаётся eventual и сама по себе не доказывает возможность привязки. Чужие и отсутствующие ресурсы не раскрываются.
- Хранить только защищённую коллекцию ссылок с отдельной ревизией; получать текущие сведения отдельно. Недоступность Flights не блокирует чтение/редактирование обычного плана, просмотр сохранённых ссылок и их удаление. Удаление поездки удаляет её связи без действий над авиазаказом.
- При ручном обновлении сначала показать сохранённый состав коллекции, затем получить статусы для её версии. Если другая вкладка снова изменила состав, сообщить об этом и предложить обновить сведения.
- Сохранить текущий M1 HTTP/snapshot protocol, CAS календаря, старые зашифрованные планы и существующие Trips/Rail/itinerary сценарии. Новая опция `Trips:FlightLinks:Enabled` выключена по умолчанию и зависит от `Trips:Enabled`; она не включает AI, itinerary или поставщиков.
- Приёмка включает приватность двух владельцев, защиту связи в системной HTTP/OTel диагностике, конкуренцию изменений, неопределённый результат записи, изменение статуса заказа, недоступность Flights и весь путь через настоящий picker с сохранением связей после перезапуска локальных сервисов на вымышленных данных.

Вне первого этапа: Hotels/Rail booking links, поиск/покупка из Trips, общая корзина и оплата, отмена/возврат из Trips, импорт пассажиров/билетов/денег, автоматический подбор подходящей поездки, перенос legs в day blocks, проверка стыковок, push/SSE и работа моделей. Существующие model/quality/target gates не меняются.

## Capabilities

### New Capabilities

- `trip-flight-order-links`: приватные версионируемые связи поездки с собственными авиазаказами, минимальное чтение их состояния, независимое удаление и сохранение границ Trips/Flights.

### Modified Capabilities

Нет. Коллекция связей — отдельный ресурс. Требования `trip-plan-workspace`, `trip-rail-intentions` и `trips-local-verification` сохраняются; новый spec добавляет собственные сценарии совместимости и сквозной приёмки.

## Impact

- Trips Core/Application: инварианты коллекции, отдельный CAS, owner guards и оркестрация чтения опубликованного Flights-контракта.
- Flights Application и `shared/dotnet/Travel.IntegrationContracts.Flights`: минимальный контракт для Trips, source-stream reader и bounded candidate listing без финансовых/пассажирских DTO. Подключение через существующие Api.Composition facades; архитектурные allowlists расширяются только для этих конкретных типов/consumer namespaces.
- Trips Infrastructure: отдельная защищённая EF-коллекция и additive source migration с FK к плану. Старый canonical plan payload и его purpose/version не переписываются. Создание/применение миграции требует отдельного применимого разрешения; данное предложение не создаёт её. Проверка готовности Trips должна обращаться к новой таблице и обязательным столбцам даже при актуальной истории миграций.
- Trips Api и `shared/ts/api-client` читают и изменяют одну коллекцию `/api/trips/{tripId}/flight-links`. `PATCH` принимает одну операцию `add` либо `remove`, внутренний `orderId` в теле JSON и `If-Match` с ETag этой коллекции. Сведения о статусах и список кандидатов доступны отдельными запросами.
- Angular: независимый раздел в существующем редакторе Trips, выбор заказа, явные действия, состояния недоступности и переход на существующую Flights order page. Работа с текущим Trusted JWT issuer и owner subject; права на booking не выдаются через Trips.
- Существующий Flights login сохраняется: внутренний order GUID может входить в его same-origin route и `redirect_uri` доверенному Keycloak. TripId, данные плана и токены туда не добавляются. Защита системной телеметрии новой пары «поездка — заказ» вносится через composable module contributions с проверкой фактического экспорта.
- В демо Playwright перехватывает запросы и проверяет действия пользователя, восстановление после потери ответа и число записей. Сквозной тест проходит через браузер, прокси, Keycloak, Host и БД и учитывает каждый `PATCH`. В Development штатные инициализаторы Host готовят Flights EF, Marten и Wolverine. После готовности Host тест создаёт вымышленные события и ожидает штатную проекцию в списке заказов.
- Новых runtime packages, внешних API или моделей не требуется. В этом change сейчас создаются только planning artifacts; код, миграции, локальные сервисы/БД, настройки окружений, stage/commit/push/PR/deploy остаются за границей текущего запроса.
