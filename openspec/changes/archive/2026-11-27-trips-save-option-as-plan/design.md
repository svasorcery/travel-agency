# Как сохранить показанный вариант в «Моих поездках»

## Context

В [текущем предпросмотре](../../../../modules/trips/Travel.Modules.Trips.Api/Endpoints/TripOptionPreviewEndpoint.cs) сервер уже проверяет владельца и возвращает структурированный результат. Строгий [TS-клиент](../../../../shared/ts/api-client/src/trips-option-api.service.ts) разбирает прежний ответ в пределах 32 КиБ. Показ карточки не создаёт записей. Обычный [TripPlanService.CreateAsync](../../../../modules/trips/Travel.Modules.Trips.Application/TripPlanService.cs) выделяет новый GUID при каждом создании. [TripPlanStore](../../../../modules/trips/Travel.Modules.Trips.Infrastructure/Persistence/TripPlanStore.cs) в транзакции PostgreSQL блокирует создание по владельцу и проверяет лимит в 100 планов. Повтор обычного POST после потери ответа может создать второй план.

Сценарии приёмки закреплены в [контракте сохранения](specs/trip-saved-options/spec.md), [дополнении к предпросмотру](specs/trip-option-preview/spec.md) и [контракте локального стенда](specs/trips-local-verification/spec.md).

## Goals / Non-Goals

Владелец сохраняет именно ту карточку, которую видел, и открывает её из обычного списка после нового входа. Один выданный выбор соответствует максимум одному плану. На исторические суммы, время и порядок точек можно опереться и после отключения генератора. Границы первого среза — существующий вымышленный Петербург, одна комната, 1–2 взрослых, 2–3 дня. Замена составляющих, ввод фразой и коммерческое оформление остаются отдельными этапами. Бюджет моделей — $0.

## Decisions

### 1. Выдать подтверждение вместе с карточкой

Новый клиент запрашивает расширенное представление существующего POST предпросмотра явным заголовком `X-Trips-Option-Save: 1`. Тело запроса по-прежнему содержит только `brief`. Без заголовка сервер возвращает в точности прежний JSON. В новом формате тело содержит `preview` и необязательный `selection` с будущим `tripId`, сроком действия и непрозрачным талоном. Старый Host может вернуть прежний ответ — новый клиент показывает его без кнопки сохранения. Ни в одном из этих путей нет второго автоматического запроса подбора.

Талон выдаётся только для `outcome=option`, авторизованному владельцу, при явном включении сохранения в разрешённом тестовом профиле. Одну проверенную модель сервер одновременно проецирует в карточку и в талон. Внутри — версия формата, нормализованный бриф, весь выбранный вариант с происхождением и ценами, криптографически случайный серверный `tripId`, время выдачи и окончания действия. Для выдачи нужны рабочие ключи Trips. Если ключи недоступны, формат не помещается в лимит или сохранение выключено, путешественник всё равно получает обычный результат подбора без доступного действия. Для `unsupported` и `noMatch` талон отсутствует. Выдача ничего не пишет в БД.

Срок первого сохранения — 15 минут реального UTC от выдачи. Защита талона должна позволять проверить подлинность и владельца также после этих 15 минут, пока действуют ключи. Срок проверяется отдельно и применяется только к первой записи. Механизм, который при расшифровании сразу отбрасывает просроченный талон, нарушил бы повтор после потерянного ответа. Исторический момент примера (27 октября 2026 года) служит подписью происхождения и не участвует в вычислении срока. Талон защищается существующим кольцом ключей Trips с отдельным назначением Data Protection, привязанным к версии и проверенным issuer/subject. Для длительного хранения используется другое назначение, включающее владельца, `tripId` и версию снимка. Разделение позволяет прочитать сохранённый вариант после истечения талона. Повторная генерация при сохранении могла бы подставить другой рейс после смены A на B; полная копия проверенного выбора в талоне сохраняет первоначальное содержание.

### 2. Одно явное действие создания

Предлагаемый маршрут — `POST /api/trips/saved-options` с телом `{selectionToken, title?}`. Форму, цены, рейсы, идентификатор владельца и готовый календарь этот маршрут от клиента не принимает. Сервер проверяет principal, формат, защиту талона и владение. Пустое или пробельное название даёт, например, «Санкт-Петербург · 28–30 октября 2026». Введённое название проходит существующий валидатор Trips. Параметры и ручные дни исходного плана создаются обычными фабриками на ревизии 1.

При первом использовании нужны включённое сохранение, пригодная схема/защита и неистёкший талон. Явный отзыв данных или смена версии профиля до первого сохранения требуют нового просмотра. Сам сохранённый снимок полностью берётся из выданного талона. Первая запись возвращает 201 и `Location`; повтор для уже созданной поездки — 200 с тем же `tripId`. Первое успешно сохранённое название остаётся у плана. Повтор не переименовывает его и не откатывает позднейшие ручные правки.

### 3. Транзакция, гонки и удаление

Предлагается добавочная EF-миграция: nullable-столбец защищённого исторического снимка в `trips.trip_plans` и короткоживущая таблица квитанций с уникальным серверным идентификатором выбора (= будущий `tripId`), владельцем и сроком талона. Квитанция не содержит маршрута, цен, названия или самого талона. Ручной план хранит NULL в новом столбце. Существующая проекция списка продолжает читать только данные, необходимые для краткого представления.

В Infrastructure выделить общий для обоих методов создания код вычисления ключа из `issuer + "\n" + subject.ToString("N")` и взятия `pg_advisory_xact_lock`. Сохранить существующее преобразование SHA-256 в big-endian Int64. В одной транзакции PostgreSQL с `READ COMMITTED` оба пути сначала получают эту блокировку и только затем читают актуальные записи владельца и считают места. Ключ из талона или `tripId` не сериализует обычное создание с сохранением варианта. Аутентификацию, проверку целостности и привязки талона к владельцу выполнить до доступа по ID. Для включённого маршрута записи действует следующий порядок.

| Под блокировкой владельца | Результат |
| --- | --- |
| Уже существует план владельца с этим ID и снимком | Вернуть его ID до проверки срока первого использования и лимита. Чтение не меняет ревизию. |
| Плана уже нет, но есть квитанция | Вернуть «выбор больше недоступен». Удалённый план не создаётся вновь. |
| Новое создание | Проверить срок, право первой записи и лимит владельца после получения блокировки. Одним commit записать план, его защищённый снимок и квитанцию. Ошибка на любом этапе откатывает всё. |

Для первого использования и очистки квитанций использовать реальные часы PostgreSQL: проверка `clock_timestamp() < expires_at` выполняется после получения блокировки; удалять квитанции можно при `clock_timestamp() >= expires_at`. Время начала ожидавшей транзакции для этой проверки непригодно. Очистка не удаляет снимок в существующем плане. При DELETE снимок уходит вместе с планом, квитанция переживает удаление до срока. Поэтому перед очисткой старый талон отклоняется по квитанции, после неё — по времени. Повтор уже сохранённого плана при включённой записи возвращает ID до проверки первого использования, смены каталога и вместимости. Если запись целиком выключена, клиент пользуется приватным GET. Старый или чужой талон не может заменить уже сохранённое содержимое.

Приёмочный стенд PostgreSQL начинает каждый из следующих опытов заново с 99 обычными планами одного владельца. Два независимых соединения, управляемый барьер после захвата блокировки и отдельный читатель после завершения позволяют задать порядок без задержек «на глаз». Обозначение «+1 снимок» означает один ненулевой исторический столбец.

| Первый держит блокировку | Ожидающий запрос | Наблюдаемый результат |
| --- | --- | --- |
| Сохранение выбора S | Повтор S | 201 и 200, один `tripId`, ревизия 1, всего 100 планов, +1 снимок и +1 квитанция. |
| Обычное создание | Сохранение S | 201 для обычного плана; 409 `Trips.CapacityExceeded` для S; всего 100, для S нет ни строки, ни снимка, ни квитанции. |
| Сохранение S | Обычное создание | 201 для S, 409 для обычного; всего 100, +1 снимок и +1 квитанция. Ещё один S возвращает 200 без изменения строк. |
| Сохранение S записало строки, затем rollback до commit | Обычное создание | Ожидающий создаёт сотый план; для S нет следов. Отдельно повторить с ожидающим S: он получает 201 и создаёт единственный полный план. |

Не сводить проверку к неравенству «не более 100»: оба запроса могли ошибочно получить отказ. Для каждой гонки сверить ответы, ID, ревизию, точные дельты строк и независимость другого владельца. Для проверки срока задержать **неиспользованный** талон до границы уже внутри ожидающей транзакции; для ранее принятого талона после той же границы ожидается 200.

### 4. Чтение, ручные правки и цена

Использовать отдельный owner-scoped `GET /api/trips/{tripId}/saved-option` при открытии поездки. Он зависит от включённого Trips и готовности хранения/ключей, работает при выключенном подборе и не вызывает загрузчик пакета, Flights, Hotels или AI. Проверить владельца в SQL до расшифрования. Чужой или отсутствующий план — одинаковый 404. Для существующего ручного плана с NULL ответ — 200 с отсутствующим вариантом. Ошибка чтения, размера, формата или расшифрования — явная недоступность; редактор различает её с обычным пустым состоянием.

У исторического GET своя регистрация при включённом Trips и отдельный декодер по версии **сохранённого снимка**. Текущий [декодер предпросмотра](../../../../shared/ts/api-client/src/trips-option.decoder.ts) требует активного discovery и сверяет хеш с текущим релизом. Исторический декодер проверяет структуру, привязку владельца/поездки, суммы, границы и допустимые источники ссылок по версии снимка; не требует текущего каталога, его хеша или ответа discovery. Отсутствие генератора в DI, истечение его данных и отключение выдачи талонов допускают чтение.

В рабочем календаре разместить отдельный слой «Сохранённый вариант» по исходным местным датам. Независимые ручные блоки, ручное жильё и ссылки на подтверждённые заказы сохраняют свои контракты. Рейсы и гостиница имеют отметку «Запланировано». Хранить исходные смещения и аэропорты, заезд/выезд и ночи, окна и порядок остановок, происхождение, дату исторической оценки, раздельные компоненты цены, их валюты, сопоставимость с бюджетом и неизвестные статьи. Дата сохранения реальная и выводится отдельно. Использовать те же правила представления денег, что в принятой карточке. Исходные 30 000 ₽ не попадают повторно в ручной подытог. При изменении дат или города показывать первоначальный вариант с его прежними датами в отдельной секции; точки не переносятся автоматически. Обычный PUT меняет только редактируемую часть и оставляет снимок целым.

### 5. Потеря ответа и границы приватности

После явного клика хранить в памяти вкладки отдельную операцию сохранения — текущий владелец/сессия, выданный ID, исходный талон и отправленное название. Двойной клик подавляется. При 201 или 200 открыть план и обновить список. Если ответ потерян, клиент переходит в состояние «Результат сохранения неизвестен»; фоновых POST нет. «Проверить сохранение» читает `GET /api/trips/{выданный ID}/saved-option`. Только положительное чтение ожидаемого снимка открывает результат. 404 до commit, отсутствие в списке и временная ошибка чтения оставляют ID и талон текущей операции в памяти. После выключения записи остаётся доступна та же проверка через GET.

[Редактор](../../../../apps/web/src/app/trips/trips-state.service.ts) сейчас снимает барьер обычного создания при обновлении списка. Развести это состояние и неопределённость сохранения выбранного варианта. Пока пользователь остаётся в этом процессе, повтор отправляет исходный POST с тем же талоном; обычный `POST /api/trips`, новый подбор и подмена выбора заблокированы. Чтобы перейти к другой поездке или изменить бриф, нужно явно выйти из восстановления с пояснением, что исходный запрос ещё мог завершиться. Выход из сессии или вкладки очищает приватный контекст. После нового входа доступен список; поздний ответ из прежнего контекста не меняет маршрут или форму.

Две проверки потери ответа имеют разные точки вмешательства. В первом случае тестовый транспорт скрывает только ответ **после** подтверждённого commit реального запроса. Во втором тестовый барьер удерживает незавершённую запись, пока UI уже видит таймаут; третье соединение/HTTP GET даёт 404. После обновления списка выполнить явный повтор, затем отпустить барьер. Проверять число и адреса POST, тот же талон в памяти теста, ответы сервера и конечные строки БД; секретное содержимое талона не включать в отчёт.

API использует строгие схемы и `no-store`, проверяет размер до десериализации, включая поток без Content-Length. Проектные пределы: прежний preview — 32 КиБ; канонические данные брифа и снимка для защиты — до 40 КиБ; талон после кодирования — до 64 КиБ; согласованный расширенный ответ и тело операции — до 128 КиБ фактических UTF-8 байтов. Измерять также защищённый столбец до материализации больших значений. Слишком большой выбор не обрезается. Не помещать талон в URL, список, постоянное хранилище браузера, SSR, ошибки, трассы или квитанции тестов. В Application использовать только порты Trips; в CI проверять отсутствие вызовов заказов, оплаты, поставщиков и модели.

### 6. Сохранить стенд между посещениями

Расширить [локальный launcher](../../../../tools/trips/local-stack.mjs) отдельным явно выбираемым сохраняемым профилем, например `saved-spb-option`, в окружении Testing. Для него выделить собственные state-каталог, Compose-проект, loopback-порты, БД и ключи. Переиспользовать проверки собственности и сценарий каталога B. `stop` и последующий `up` этого профиля сохраняют его данные; `destroy --yes` удаляет только подтверждённые ресурсы этого экземпляра. При коллизии портов или чужом состоянии запуск отказывает до изменений. Для остановленного сохраняемого профиля предусмотреть явный режим возобновления для исторического чтения (предлагаемый ключ `up --read-saved-only`). Источником настроек остаётся launcher: перед переходом проверить владельца, daemon, незанятые порты, неизменность исходной конфигурации и остановку служб; выбрать заранее определённый override и проверить фактические флаги запущенного Host. Оба поддерживаемых режима используют прежний ID стека, том и кольцо ключей. Отказ или прерывание перехода должно позволить продолжить только из проверенного состояния; ручное редактирование Compose по-прежнему отвергается существующей [проверкой владения и файлов](../../../../tools/trips/local-stack.mjs).

Обязательная приёмка: сохранить B, зафиксировать ID, ревизию, SHA-256 канонического снимка и безопасный отпечаток ключей; закрыть браузер и подтвердить остановку Host, Keycloak и PostgreSQL. Возобновить их в режиме чтения: Trips включён, прогулки, option preview, выдача и запись выбора выключены. Через новый браузерный контекст и новый PKCE-вход открыть ID из списка без талона. Сверить ревизию, хеш, видимые значения B, пометки «Запланировано» и реальные счётчики: на пути исторического чтения ноль вычислений варианта, чтений пакета, коммерческих вызовов и записей. На отдельной копии испортить снимок или использовать недоступный ключ и подтвердить явную недоступность. Смена B на A при работающем генераторе — дополнительная проверка.

Обычное демо остаётся на реальном времени; действующие `spb-option --inspect` и E2E по завершении по-прежнему убирают свои ресурсы. Зафиксировать в руководстве, какой режим позволяет вернуться к поездке завтра.

## Risks / Trade-offs

- Большая карточка может пройти лимит обычного preview и выйти за предел расширенного ответа. Проверять размер обеих форм на границе; при невозможности выдачи талона оставить пользователю просмотр.
- Снимок теоретически может перепутаться с ручным планом или заказом. В проверке интерфейса сравнить подписанные «Запланировано» рейсы и жильё, отдельную цену и состояние ручных блоков до и после обычной правки.
- Ошибка подтверждения commit оставляет неопределённость и у клиента, и у сервера. Повтор использовать только через тот же ID и чтение под блокировкой владельца; сверять итоговые количества в отдельном соединении PostgreSQL.

## Migration Plan

Принятый порядок — **схема → новый Host с выключенной записью → включение сохранения**. Общая [готовность Trips](../../../../modules/trips/Travel.Modules.Trips.Infrastructure/Readiness/TripsReadiness.cs) рассматривает pending migrations; для этой миграции исключение не вводить. Старт приложения не применяет SQL. Для выкладки нужны проверенные EF-миграция и SQL, отдельное разрешение на их применение к выбранной БД и контроль наличия столбца, таблицы, уникального ключа и индекса срока.

| Этап репетиции на одноразовой БД | Критерий перехода |
| --- | --- |
| Прежний Host + прежняя схема | Создать и повторно открыть ручной план. Отдельно проверить, что новый Host со старой схемой даёт Trips unready даже с выключенным сохранением и не меняет БД. Трафик продолжает обслуживать прежний Host. |
| Добавочная миграция + прежний Host | Исходный план читается без изменения ревизии, обычное создание и чтение нового ручного плана проходят. Для обоих исторический столбец NULL. |
| Расширенная схема + новый Host, сохранение выключено | Готовность проходит, оба старых плана открываются и создаётся ещё один ручной план; POST новой функции закрыт. Только после этого включить сохранение на разрешённом профиле и проверить первую запись и чтение снимка. |

При откате сначала отключить выдачу/первую запись и сохранить совместимое чтение. Остановить записи перед проверкой наличия снимков и действующих квитанций. Пока есть такие данные либо проверка недоступна, оставить расширенную схему и читающую версию. При доказанном нуле на одноразовой БД проверить разрешённый откат и обычный GET/POST на соответствующей старой схеме/Host. Откат старого бинарника с сокрытием исторического слоя не считается полным восстановлением сервиса.
