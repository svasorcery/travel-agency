# Реализация и приёмка сохранения поездки

## 1. Снимок и подтверждение выбора

- [x] 1.1 Определить версию исторического снимка и его строгий кодек в Trips. На эталонах A/B, коротком RT3/H3 с ценой net и бюджете 1 EUR проверить полный цикл записи/чтения: исходный бриф, локальные даты и смещения обоих рейсов, ночи, окна, упорядоченные точки, оценки и неизвестные расходы, версия правил, релиз и атрибуция. Отдельно проверить неизвестную версию и превышение лимита.
- [x] 1.2 Реализовать защищённый владельцем талон с серверным ID и 15 минутами на первую запись. Проверить подлинность независимо от истечения срока, чтение теми же ключами после рестарта, чужой issuer/subject, подмену байтов и назначения защиты. Два независимых выбора получают разные ID.
- [x] 1.3 Добавить согласование формата preview, отдельный выключенный по умолчанию флаг сохранения и описание в OpenAPI. Через настоящий HTTP pipeline проверить ровно один POST, прежнюю форму ответа без заголовка, расширенную карточку, отсутствие талона для noMatch/unsupported и рабочий просмотр при недоступной защите. Проверить пределы 32/40/64/128 КиБ из design.md на соответствующих границах и нулевые записи при выдаче.

## 2. Атомарное создание и восстановление результата

- [x] 2.1 Подготовить добавочную EF-миграцию, SQL, проверки структуры и readiness по матрице Migration Plan. На отдельно разрешённой одноразовой БД: прежний Host создаёт/читает ручной план; новый Host на старой схеме с флагом off остаётся unready без автомиграции; после расширения старый Host читает исходный и создаёт новый ручной план; новый Host при off читает оба и выполняет ручное создание. Проверить NULL и предел чтения столбца. Только затем включить новую запись. Для отката с остановленными писателями проверить отказ при живом снимке, квитанции или неизвестном состоянии и разрешённый путь при нуле.
- [x] 2.2 Выделить общую с обычным созданием блокировку владельца и атомарную запись. На исходных 99 планах воспроизвести барьерами четыре строки таблицы design.md: один талон дважды (201/200, один ID); обычное создание первым (201 и 409, ноль следов выбора); сохранение первым (201 и 409, повтор победителя 200); откат проигрывающей транзакции до commit (ожидающий создаёт сотый). Вариант с ожидающим повтором того же талона после rollback даёт 201. В каждом случае третьим соединением проверить точные ID, ревизию 1, 100 строк, дельты снимков/квитанций и независимость другого владельца.
- [x] 2.3 Реализовать порядок проверки подлинности, владельца, существующего плана, квитанции, первого срока и лимита. Проверить повтор после commit при 100 планах и после переименования/ручной правки с тем же ID и прежней достигнутой ревизией. У истёкшего талона для живого сохранённого плана — 200, у неиспользованного — отказ. Удалить план и повторить до/после очистки квитанции; удержать запрос за блокировкой до границы срока. Проверить отсутствие повторной записи при едином времени PostgreSQL для admission и cleanup.
- [x] 2.4 Подключить приватные POST сохранения и GET исторического варианта через Trips Api, добавить схемы и исходы в OpenAPI. Проверить 201/Location и 200 для одного ID, отказ чужому владельцу/изменённому талону, отсутствие нового плана при смене профиля до первой записи, отказ неизвестным полям/присланным ценам, лимиты тела с неизвестной длиной и no-store. Проверить отключение записи при работающем чтении, три исхода GET (вариант, обычный план, недоступное хранилище/ключи) и одинаковый 404 для чужого и отсутствующего плана. Действующие проверки коммерческих портов должны фиксировать ноль вызовов.

## 3. Действия путешественника и календарь

- [x] 3.1 Добавить в типизированный клиент согласованный preview и команды сохранения/проверки; в Angular показать «Сохранить поездку» только для текущего выбора. Проверить мышь и клавиатуру, название из формы и автозаголовок при пустом вводе, переход к созданной поездке и одну строку в списке. Регрессиями подтвердить обычное «Создать» и работу нового клиента с прежним форматом preview.
- [x] 3.2 Ввести отдельное состояние неопределённого сохранения. Проверить потерю ответа после commit и GET по исходному ID, а также 404 при удержанном commit, обновление списка и явный повтор тем же талоном. Ни один GET не вызывает повторный POST; общий «Создать» заблокирован до явного выхода из восстановления. Проверить двойной клик, новый подбор только после отказа от восстановления, сброс при смене владельца/выходе и игнорирование запоздалого ответа. Подтвердить отсутствие талона в URL, логах, browser storage и SSR.
- [x] 3.3 Ввести исторический декодер по версии снимка, независимый от текущих discovery, хеша релиза и регистрации генератора. Отрисовать исходные локальные дни, «Запланировано», ставки и валюты без двойного учёта. Проверить обычный PUT, смену дат/города, старые ручные планы, workspace v1/v2 и отдельные ссылки Flights/Hotels. При недоступном ключе или испорченном снимке интерфейс показывает ошибку; только настоящий NULL даёт отсутствие исторического слоя.
